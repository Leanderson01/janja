# Fase 8.5 Plano 16: Prévias de link na interface — Summary

**Mensagem com link ganha um cartão com site, título, descrição e imagem, abaixo do texto
e acima dos anexos. Mensagem sem link não monta componente nenhum, não abre subscription
nenhuma e não custa nada. Enquanto não há dado, nada é renderizado — nem esqueleto, nem
espaço reservado — e a busca no servidor é pedida no máximo uma vez por URL, inclusive
quando a lista remonta a linha ao paginar.**

## `firstLinkOf` — as decisões que evitam prévia errada

Função pura, 17 testes. O que ela recusa importa mais do que o que ela aceita:

| Entrada | Saída | Por quê |
|---|---|---|
| `liguei pro www.exemplo.com hoje` | `null` | Adivinhar link sem esquema é o que transforma "manda o arquivo.zip" e "às 9h.qualquer" em requisição de servidor e cartão errado. Exigir `http://`/`https://` custa a prévia de quem colou sem esquema — o que é **invisível**, porque nada é renderizado nesse caso |
| `javascript:alert(1)`, `data:text/html,…`, `ftp://`, `file:///C:/…` | `null` | O cliente é um Electron. Esquema executável ou local não entra nem no caminho da action |
| `https://um.com e https://dois.com` | `https://um.com` | Uma prévia por mensagem. Cinco links seriam cinco requisições e um muro de cartões empurrando a conversa para fora da tela |
| `achei aqui: https://exemplo.com/post.` | `https://exemplo.com/post` | Link no fim da frase é o caso mais comum de todos |
| `(veja https://exemplo.com/post)` | `https://exemplo.com/post` | Fechamento **sobrando** é pontuação do texto |
| `https://pt.wikipedia.org/wiki/Java_(linguagem)` | inteiro | Fechamento **balanceado** faz parte da URL. Aparar sempre quebraria a Wikipédia, que é exatamente o tipo de link que este grupo posta |
| `xhttps://exemplo.com`, `mailto:eu@https://x.com` | `null` | O "http" ali é pedaço de outra coisa |
| `http://`, `olha https://.` | `null` | Sobrou esquema sem host. Sem esta peneira, a action gastaria uma linha de cache `failed` para descobrir o óbvio |
| URL de 2100 caracteres | `null` | Teto de 2000 |

A peneira final é `new URL()` com exigência de host — o que sai daqui é URL de verdade.

## O cartão: os três estados que não desenham nada

Esta é a parte que decide se a feature ajuda ou atrapalha, e ela é quase toda sobre **não
renderizar**:

1. **`undefined`** (a query ainda não respondeu) → `null`, e **nenhuma busca é pedida**.
   Disparar aqui faria toda mensagem com link pedir busca no primeiro frame, antes de a
   query dizer que o dado já existia.
2. **`null`** (cache frio) → `null` na tela, e a busca é pedida **uma vez**.
3. **`status: 'failed'`** → `null`. É o caso **normal**, não a exceção: site fora do ar,
   página sem `og:title`, URL recusada pela guarda de destino privado, ou **cadeia de
   redirect recusada** (o `fetchValidatingEachHop` do commit `508bb72`, posterior ao Plano
   08.5-15). Todos chegam à UI com exatamente o mesmo `status`, e **o motivo da recusa não
   vai para a tela de propósito** — quem descobre por que um endereço foi recusado aprende
   sobre a rede interna do servidor. Nenhum estado novo, nenhuma mensagem específica.
4. **`ok` sem título** → `null`. Cinto de segurança: o servidor nunca grava isso (é regra
   escrita em `convex/linkPreviews.ts`), mas se um dia gravar, o certo é não mostrar nada
   em vez de um retângulo vazio no meio da conversa.

**Nada de esqueleto, placeholder ou altura reservada.** A lista de mensagens tem lógica de
scroll sensível a altura (CHAT-04/CHAT-14, já verificadas com usuário real): um bloco que
aparece e depois muda de tamanho empurra o histórico debaixo do cursor de quem está lendo.
O cartão só existe quando há conteúdo definitivo para ele.

### A guarda de disparo único tem DOIS níveis, e o segundo é o que importa

O plano pedia um `useRef`. Um `useRef` sozinho **não resolve o caso que o próprio plano
descreve** (remontagem por scroll/paginação): ref vive na instância, e a lista remonta
linhas ao paginar e ao trocar de canal — a instância nova começa com o ref zerado.
Enquanto a action ainda não gravou, o cache continua `null`, e cada remontagem dispararia
a busca de novo.

Por isso são dois:

```
requestedRef (useRef)  → a mesma instância não redispara em re-render
requestedUrls (Set de módulo) → nenhuma instância nova redispara na mesma sessão
```

As duas marcas são feitas **ANTES** da chamada, nunca no `.then` — lição nº 3 do
HANDOFF.md, a mesma que produziu a conexão duplicada ao LiveKit. Se a action rejeitar, o
pedido continua marcado como feito: o servidor já gravou `failed` no cache, e insistir
daqui seria re-sondar um site quebrado a cada render.

Uma URL só sai do `Set` quando o app recarrega. Isso é escolha, não esquecimento.

## CSP: conferida, não afrouxada

```

```

`img-src` já aceitava `https:` desde antes (avatares do Google/WorkOS, e o Plano 08.5-14
confirmou que cobre imagem de anexo). A `og:image` de terceiro entra nessa mesma regra.
**Zero mudança no `index.html`** — o arquivo nem está no diff desta execução.

O que a CSP recusa e o código trata: `og:image` servida em `http://`. O Chromium bloqueia,
o `onError` esconde a imagem, e o cartão continua de pé com título e descrição. (O
servidor já descarta `og:image` que não seja http/https, então `javascript:`/`data:` nunca
chegam a um `<img src>` aqui.)

## Custo zero para quem não posta link — o mecanismo, não a intenção

```tsx
const link = firstLinkOf(message.content)
…
{link ? <LinkPreviewCard url={link} /> : null}
```

Mensagem sem link **não monta o componente**, e componente não montado não chama
`useQuery` — nenhuma subscription é aberta, nenhuma chamada de servidor acontece. Não é
uma otimização que alguém pode desfazer sem perceber: é a estrutura. Numa lista paginada
de 30 em 30 mensagens, esse é o detalhe que decide se a feature é aceitável.

`firstLinkOf` roda por mensagem renderizada: é uma regex sobre uma string curta, sem
alocação relevante. Não foi memoizada — `useMemo` aqui custaria mais em ceremônia do que
economiza.

**Ordem visual: texto → prévia → anexos.** Anexo é conteúdo que a pessoa mandou; prévia é
enfeite derivado do texto. A prévia fica antes para não separar a mensagem do que ela
carrega.

**Nada da lógica de scroll foi tocado:** `data-unread-divider`, o `key` das mensagens, os
dois efeitos de scroll e a compensação de `scrollHeight` estão byte a byte iguais. O diff
de `MessageList.tsx` é de **12 linhas acrescentadas, zero removidas**.

## Desvios do plano

### 1. [Rule 2 — lacuna crítica] Guarda de módulo além do `useRef`

- **Encontrado em:** Task 2, ao escrever a guarda que o plano pede.
- **Problema:** o plano pede um `useRef` "para não redisparar quando o componente remonta
  por causa de scroll/paginação". Um `useRef` **não faz isso** — ele morre com a instância.
  Implementar só o que estava escrito entregaria uma guarda que falha exatamente no cenário
  que o plano cita.
- **Correção:** o `useRef` continua (protege re-render) e um `Set` de módulo foi
  acrescentado (protege remontagem). Provado por teste que desmonta e remonta.
- **Commit:** `eb611c4`

### 2. [Rule 2 — lacuna crítica] Peneira de URL válida em `firstLinkOf`

- **Encontrado em:** Task 1.
- **Problema:** o plano pedia apenas regex + poda de pontuação. Com isso, `http://` solto
  ou `https://.` (o que sobra depois da poda) seriam "links" e iriam para a action, que
  gastaria uma linha de cache `failed` para descobrir o óbvio — e o app pediria trabalho
  de servidor por causa de pontuação.
- **Correção:** `new URL()` com exigência de host e de esquema http/https como última
  peneira. Dois testes.
- **Commit:** `6eb9196`

### 3. [Rule 2 — lacuna crítica] Fronteira à esquerda no reconhecimento do link

- **Encontrado em:** Task 1, escrevendo os testes.
- **Problema:** a regex ingênua aceita `xhttps://exemplo.com` e `mailto:eu@https://x.com`,
  onde o "http" é pedaço de outra coisa.
- **Correção:** fronteira que recusa caractere de palavra/endereço antes do esquema, mas
  **permite** aspas, parênteses e `<` (link colado entre aspas é escrita normal — o
  primeiro corte que escrevi quebrava esse caso e o teste pegou).
- **Commit:** `6eb9196`

### 4. [Acréscimo registrado] Arquivo de teste além do `files_modified`

Acrescentado porque, sem deployment do Convex nesta máquina, este é o **único** lugar onde

render" e "link cuja busca falhou não deixa cartão vazio". Sem ele, as duas seriam

É arquivo **novo**, adjacente ao componente deste plano, sem executor paralelo rodando —

## Roteiro para o checkpoint humano (Plano 08.5-17)

Ordem obrigatória: **`npx convex dev --once` PRIMEIRO** (sem ele a tabela e as duas funções
não existem no deployment, e toda mensagem com link vira erro de query, não cartão vazio).

**Item 1 é o mais importante desta lista inteira — é o risco real da feature.**

1. **[O RISCO DA FEATURE] A prévia que chega DEPOIS não empurra o scroll.**
   Com o histórico do canal aberto e **rolado para o meio** (não no fim), peça para alguém
   postar um link — ou poste de outra máquina. Enquanto a busca acontece (até 5 s), a
   mensagem existe **sem** cartão; quando o cache grava, o cartão aparece e a mensagem
   **cresce**. Confirmar que o que você estava lendo **não pulou**. Repetir rolando devagar
   perto do fim da lista. Se pular, o conserto é reservar altura só depois que o cartão
   existe — não antes.
2. **Uma mensagem com link vira cartão.** Poste `https://github.com` num canal. Em poucos
   segundos deve aparecer site, título, descrição e (se o site der `og:image`) imagem.

3. **A imagem CARREGA de verdade** — é a prova de que a CSP não precisou mudar. Poste um

   é `Refused to load the image` — e aí a correção é em `img-src`, não no componente.
4. **`max-h-40` não estoura o layout** com imagem muito alta ou muito larga, e o cartão não
   passa de ~28 rem mesmo com título e descrição longos (o `line-clamp` corta em 2 e 3

5. **Link quebrado não deixa lixo na tela.** Poste `https://esse-dominio-nao-existe-9x8y.com`

6. **[Privacidade — a razão de o backend existir] O cliente NÃO busca o site.**
   Com o DevTools na aba Network, poste um link. Deve haver tráfego para o Convex e

   Plano 08.5-15 furou.
7. **A busca acontece UMA vez.** No dashboard do Convex, aba de logs, poste o mesmo link
   **duas vezes** e em **dois canais diferentes**: só a primeira postagem deve gerar

   **nenhuma** nova execução. É a prova do cache compartilhado por URL.
8. **Mensagem sem link não fala com o servidor.** No dashboard, confirmar que uma conversa
   normal (sem links) não gera nenhuma chamada a `getPreview`.
9. **O link do cartão abre no NAVEGADOR do sistema**, não numa janela do Electron. Clicar

10. **URL privada é recusada em silêncio.** Poste `http://192.168.0.1` e `http://localhost:3000`.
    Esperado: nenhum cartão, e **nenhuma pista na tela** sobre o motivo. No dashboard, a
    linha de cache correspondente deve estar `failed`.
11. **[Novo desde o commit `508bb72`] Cadeia de redirect.** Poste um link encurtado
    (`bit.ly`, `t.co`) que aponte para um site público: deve virar cartão do **destino
    final**. O teto é de 3 saltos — um encurtador em cima de outro em cima de outro deixa
    de virar cartão, e isso é o comportamento certo, não defeito.
12. **Mensagem com vários links** mostra **um** cartão só (o do primeiro link). Mensagem com
    `www.exemplo.com` (sem esquema) **não** mostra cartão nenhum — é a decisão de escopo,
    não bug.
13. **Prévia + anexo na mesma mensagem:** a ordem na tela deve ser texto → cartão de prévia
    → anexos.
14. **DM não tem prévia** e isso é esperado: postar um link numa DM deve mostrar só o texto.
