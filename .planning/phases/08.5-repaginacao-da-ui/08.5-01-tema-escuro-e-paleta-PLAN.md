  <name>Task 1: Forçar tema escuro e declarar idioma/título/theme-color no documento</name>
  <files>src/renderer/index.html</files>
  <action>
    Editar APENAS a tag `<html>` e o `<head>` de `src/renderer/index.html`:

    1. `<html>` → `<html lang="pt-BR" class="dark">`.
       - `class="dark"` é o que ativa o bloco `.dark` de `main.css`
         (`@custom-variant dark (&:is(.dark *))` é seletor de CLASSE, não
         `prefers-color-scheme`). Sem ela, `:root` (branco) vence.
       - Fixar no HTML e não em `main.tsx` de propósito: sem alternância de
         tema, um `classList.add('dark')` em JS só acrescentaria um flash de
         tema claro no boot e um lugar a mais para esquecer.
    2. `<title>Electron</title>` → `<title>janja</title>`.
    3. Acrescentar `<meta name="theme-color" content="#0a0a0a" />` — é o
       equivalente sRGB de `--background` do bloco escuro (`oklch(0.145 0 0)`).
    4. Acrescentar um comentário HTML curto explicando por que a classe está
       fixa aqui (mesmo estilo dos comentários que já documentam a CSP neste
       arquivo): "tema escuro é fixo por decisão de produto; não existe toggle".

    NÃO tocar no bloco de `Content-Security-Policy` nem no seu comentário —
    ele existe por um defeito real da Fase 2 (WebSocket do Convex recusado
    pelo Chromium) e não tem relação com tema.
  </action>
  <verify>
    `grep -n 'class="dark"' src/renderer/index.html` retorna a linha do `<html>`;
    `grep -n 'lang="pt-BR"' src/renderer/index.html` retorna a mesma linha;
    `grep -c "connect-src" src/renderer/index.html` continua retornando 1 (CSP intacta);
    `npm run build` passa.
  </verify>

  <files>src/renderer/src/assets/main.css</files>
  <action>
    Acrescentar três pares de token seguindo EXATAMENTE o padrão do
    `--destructive` já presente (valor no `:root`, valor no `.dark`, mapeamento

    ```css

      --success-foreground: oklch(0.985 0 0);

      --warning-foreground: oklch(0.145 0 0);
      --highlight: oklch(0.52 0.2 264);
      --highlight-foreground: oklch(0.985 0 0);
    ```

    No bloco `.dark` (o que o app realmente usa):
    ```css
      --success: oklch(0.72 0.17 150);
      --success-foreground: oklch(0.145 0 0);
      --warning: oklch(0.8 0.15 85);
      --warning-foreground: oklch(0.145 0 0);
      --highlight: oklch(0.6 0.19 264);
      --highlight-foreground: oklch(0.985 0 0);
    ```
    E, no MESMO bloco `.dark`, trocar `--ring: oklch(0.556 0 0);` por
    `--ring: var(--highlight);` — é o que faz o anel de foco (aplicado a todo
    elemento por `@layer base { * { @apply outline-ring/50 } }`) passar a usar
    o tom de destaque sem nenhum plano precisar tocar em componente.
    Deixar o `--ring` do `:root` como está.

    No bloco `@theme inline`, logo abaixo de `--color-destructive`:
    ```css
      --color-success: var(--success);
      --color-success-foreground: var(--success-foreground);
      --color-warning: var(--warning);
      --color-warning-foreground: var(--warning-foreground);
      --color-highlight: var(--highlight);
      --color-highlight-foreground: var(--highlight-foreground);
    ```

    Acrescentar um comentário CSS acima dos tokens novos registrando as regras
    de uso, porque é onde quem for mexer vai olhar:
    - `--highlight`: matiz ~264, a mesma família do `--sidebar-primary` órfão
      do boilerplate. Uso permitido: estado ativo/selecionado, anel de foco,
      marcador de não-lido. Nunca decoração.
    - `--success`/`--warning`: significado semântico (online, falando,
      compartilhando, qualidade de conexão, reconectando). NÃO são destaque e
      não contam contra a regra de "um único tom".

    Não remover `--sidebar-primary` nem qualquer outro token existente: são
    boilerplate do `shadcn init`, não fazem mal, e removê-los é ruído de
    diff num arquivo que outros planos vão ler.
