### 4. Como o layout troca sem mexer no tile

Três mecanismos, nenhum deles remove o componente da árvore:

| Mecanismo | Onde | Por quê |
|---|---|---|
| `hidden` no container do vídeo | layout `tiles` com track no ar | O tile fica montado, com `display:none` no container. O `<video>` continua anexado e a inscrição continua viva. |
| `order-1/2/3` do flexbox | vídeo, grade e faixa | Vídeo em cima no modo `share`, embaixo no modo `tiles`. **Reordenar visualmente sem mover o nó na árvore** — mover seria desmontar e remontar. |
| `hidden` em INVÓLUCROS | barra do palco e faixa | Elas assinam queries do Convex; piscar subscrição a cada expandir/restaurar é ruído gratuito. |

Detalhe que quase virou defeito e virou comentário no código: o `hidden` **não pode** ir no
mesmo elemento que tem `flex`. Os dois são utilitários de *display*, e qual vence depende
da ordem no CSS gerado, não da ordem no atributo `className`. Por isso a barra e a faixa
somem através de um invólucro sem utilitário de display.

## (b) A máquina de estados de layout — o que o Plano 08.5-11 precisa saber

`CallStage.tsx` edita o mesmo arquivo em seguida. O estado é este, e é todo local:

```ts
type StageLayout = 'tiles' | 'share' | 'share-expanded'
```

**Não vai para o `SelectionContext` nem para o `localStorage`**, de propósito: é estado de
momento, e persistir "expandido" faria o app abrir numa call antiga em tela cheia.

| Gatilho | Transição |
|---|---|
| Montagem com tela já no ar | inicializa em `share` (nada de piscar `tiles`) |
| Primeira tela aparecendo (`0 → n`) | `→ share` |
| Segunda tela aparecendo (`n → n+1`, `n>0`) | **nada**: se o usuário acabou de ocultar, reabrir na cara dele seria briga |
| Última tela saindo (`n → 0`) | `→ tiles`, de qualquer layout — inclusive do expandido, senão o usuário fica preso numa tela cheia vazia |
| Botão `Maximize2` | `share → share-expanded` |
| Botão `Minimize2` / tecla **Esc** | `share-expanded → share` |
| Botão `EyeOff` ("Ocultar tela") | `share`/`share-expanded` → `tiles`, **sem parar o compartilhamento** |
| Botão `Eye` ("Mostrar tela") | `tiles → share` (ver desvio 1) |

As transições automáticas são feitas **durante a renderização**, não num `useEffect`:

```tsx
const [previousShareCount, setPreviousShareCount] = useState(shareCount)
if (previousShareCount !== shareCount) {
  setPreviousShareCount(shareCount)
  if (shareCount === 0) setLayout('tiles')
  else if (previousShareCount === 0) setLayout('share')
}
```

É o padrão documentado do React para "estado que se ajusta quando uma entrada muda". A
primeira versão usava `useEffect` + `useRef` e **o eslint do repo reprovou**
(`react-hooks/set-state-in-effect`, erro, não aviso) — com razão: pelo caminho do efeito o
palco apareceria um quadro inteiro com o layout velho antes de se corrigir.

O Esc só existe enquanto expandido (listener registrado e removido pelo layout) e ignora
eventos com `defaultPrevented`, que é a única defesa possível daqui contra roubar o Esc de
uma camada do Radix aberta por cima. **Não é garantia** — o Radix nem sempre chama
`preventDefault` ao fechar. Item do checkpoint humano.

## (d) A barra do palco e a janela estreita

O botão de membros é o **mesmo** do `ChannelHeader`: `useLayout()` do Plano 08.5-05, ícone
`Users`, `Tooltip`, `aria-label` que acompanha a ação e `aria-pressed` com o estado. Entrar
numa call não podia tirar do usuário um controle que ele tinha na visão de texto — e é
justamente na call que os 240px fazem mais falta, porque a área grande é vídeo.

Na janela mínima (900×600, com rail 72 + sidebar 240 + membros 240 dividindo a largura),
**só o nome cede**: `min-w-0 flex-1 truncate` no nome (os dois são necessários — item flex
tem `min-width: auto` e o `truncate` sozinho não vence isso), `shrink-0` na contagem e no
grupo de botões. Nos três layouts a faixa rola horizontalmente em vez de quebrar.

Todos os botões de ícone têm `aria-label` e tooltip, e herdam o anel de foco do `Button`.
No layout expandido eles são a **única** saída além do Esc, e por isso ficam num overlay
com fundo (`bg-background/90` + borda) no canto superior direito do vídeo.

## (e) O fundo do palco (`bg-stage`) — decisão que chegou durante a execução

O usuário aprovou, em 2026-08-19, deixar o palco visivelmente mais escuro que a área de
texto — a pendência que o Plano 08.5-03 tinha deixado aberta. O token nasceu **fora deste
plano** (commit `affdd51`, em `main.css`, arquivo que não é meu e não foi tocado):
`--stage: oklch(0.1 0 0)` no tema escuro, contra `oklch(0.145 0 0)` do `--background`.

Aplicado **só na raiz do palco** (`bg-stage text-stage-foreground`). Barra, ladrilhos e
faixa continuam sem fundo próprio, porque o ponto do fundo escuro é que o conteúdo se
destaque **contra** ele.

Uma consequência que precisou de decisão: os badges de mute/compartilhando usam
`ring-2 ring-background` para simular um recorte no fundo atrás do avatar. Com o palco em
`--stage`, esse anel viraria um halo mais claro. Na **faixa** (que só existe dentro do
palco) o anel virou `ring-stage`. Na **grade** ele continua `ring-background`, porque a
grade também é renderizada na prévia de canal de voz, que fica sobre `--background`.

**A classe chega ao CSS gerado** — Tailwind v4 só emite classe que aparece em código
escaneado, e este token nasceu sem nenhum uso (lição do Plano 08.5-01):

```
$ npm run build && grep -o "\.[a-z-]*stage[a-z-]*[^,{]*[,{]" out/renderer/assets/index-*.css | sort -u
.bg-stage {
.ring-stage {
.text-stage-foreground {

$ grep -o -- "--stage:[^;]*;" out/renderer/assets/index-*.css | sort -u
--stage: oklch(10% 0 0);
--stage: oklch(94% 0 0);
```
