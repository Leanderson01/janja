## Summary

A base de código da F3-F8 já segue boa parte das convenções do brief: todo
`Avatar` tem `AvatarFallback`, todo `Dialog` tem `DialogTitle`,
`ScrollArea`/`Separator` já são usados na maioria dos lugares certos, e os
itens clicáveis da sidebar de canais e do rail de servidores já são
`<button>` de verdade (navegáveis por Tab, não `<div onClick>`). O trabalho
desta fase não é "consertar tudo do zero" — é fechar um conjunto pequeno e
bem localizado de lacunas, todas mapeadas abaixo com arquivo e linha.

Três achados mudam o plano mais do que o esperado. **Primeiro:** o app hoje
renderiza no tema **claro**, não escuro — nenhuma linha de código em todo
`src/renderer` aplica a classe `.dark` ao `<html>`/`<body>`, apesar de todo
`main.css` e todo componente terem sido escritos assumindo o tema escuro do
Discord. Isso não é uma preferência a decidir, é um defeito a corrigir, e
provavelmente pertence ao primeiro plano desta fase (todo o resto depende de
ver a cor certa). **Segundo:** a paleta atual é 100% monocromática (chroma
zero em quase todos os tokens OKLCH) — não existe *nenhum* tom de destaque
definido hoje, exceto um `--sidebar-primary` azul-violeta que existe no CSS
mas não é usado em lugar nenhum do código. O brief pede "um único tom de
destaque"; a fase precisa decidir esse tom (reaproveitar o token órfão ou
criar um novo) e depois trocar as ~15 ocorrências de cor direta
(`green-500`, `red-500`, `amber-500`) por tokens semânticos. **Terceiro:** o
tratamento de Enter no composer (`MessageInput.tsx`) hoje **não verifica
composição de IME** — é o bug exato que o `CONTEXT.md` decidiu corrigir, já
localizado em `src/renderer/src/components/shell/MessageInput.tsx:35-40`.

**Recomendação principal:** ordenar os planos desta fase assim — (1) correção
de tema escuro + definição do tom de destaque + tokens semânticos que faltam
(`--success`/`--warning` ou equivalente), porque tudo mais depende de ver a
cor certa; (2) composer (IME + Enter/Shift+Enter + Sonner) e instalação dos
componentes shadcn que faltam; (3) menus (Collapsible/DropdownMenu/
ContextMenu); (4) acessibilidade/teclado + janela estreita, que são
principalmente verificação sobre o que os itens 1-3 já deixaram pronto.

### Composer e IME — o bug real
`src/renderer/src/components/shell/MessageInput.tsx:35-40`:
```tsx
function handleKeyDown(event: KeyboardEvent<HTMLTextAreaElement>): void {
  if (event.key === 'Enter' && !event.shiftKey) {
    event.preventDefault()
    submit()
  }
}
```
Não checa `event.nativeEvent.isComposing`. É o único composer do app — usado
tanto em canal de servidor (`ConversationArea.tsx:265`) quanto em DM
(`DmConversationView.tsx:85`) — corrigir este arquivo corrige os dois
lugares.

### Tema escuro não aplicado — achado com prioridade alta
`src/renderer/index.html` não tem `class="dark"` no `<html>`, e uma busca
por `documentElement`, `classList`, `'dark'` em todo `src/renderer/src`
não retorna nenhuma ocorrência. `main.css` define `:root { ... }` (tema
claro) e `.dark { ... }` (tema escuro) via `@custom-variant dark
(&:is(.dark *));` (seletor de classe, não `prefers-color-scheme`) — sem a
classe, **todo o app renderiza no tema claro** definido em `:root`
(`--background: oklch(1 0 0)` = branco). Como nenhum plano desde a F3 teve
verificação visual real em Windows confirmada nos SUMMARYs lidos (a F3
rodou sob Xvfb e falhou por GPU, sem confirmação visual), é plausível que
ninguém tenha notado. Este projeto não tem nenhum toggle de tema nem
intenção de ter um (BRIEF pede "interface dark moderna", CONTEXT não
menciona alternância) — a correção mais simples é forçar `class="dark"` no
elemento raiz permanentemente, sem lógica condicional.

### `border-t`/`border-*` sem cor explícita — não é bug, é o padrão do projeto
Tailwind v4 mudou a cor padrão de `border-*` de `gray-200` (v3) para
`currentColor` (confirmado via `tailwindcss.com/docs/upgrade-guide` — nota
oficial: "We've changed this to `currentColor` in v4 [...] make sure you
specify a color anywhere you're using a `border-*` [...] utility"). Isso
normalmente quebraria bordas "invisíveis" em qualquer projeto migrado sem
cuidado. **Este projeto já se protegeu disso**: `main.css:113-116` tem
```css
@layer base {
  * { @apply border-border outline-ring/50; }
}
```
que aplica `border-color: var(--border)` a todo elemento via seletor
universal — é o próprio boilerplate padrão do `shadcn init` para Tailwind
v4. Ou seja, `border-t` sem sufixo de cor (`UserPanel.tsx:38`) **funciona
corretamente** hoje, herdando `--border` do seletor universal — não é um
achado acionável, só documentado aqui para não ser redescoberto como "bug"
achando que precisa de `border-border` explícito em todo lugar.

## Arquitetura / Padrões

### Padrão de IME seguro para o composer
Fonte: comportamento padrão de `KeyboardEvent.isComposing` (WHATWG UI
Events spec) e prática consolidada de comunidade (verificado via WebSearch,
múltiplas fontes concordantes: `dev.classmethod.jp`,
`witch.work`, MDN). Fix mínimo em `MessageInput.tsx`:
```tsx
function handleKeyDown(event: KeyboardEvent<HTMLTextAreaElement>): void {
  if (event.key === 'Enter' && !event.shiftKey && !event.nativeEvent.isComposing) {
    event.preventDefault()
    submit()
  }
}
```
**Por que não precisa do fallback `keyCode === 229`:** esse fallback existe
para navegadores legados (IE/Edge antigo) e para uma inconsistência
conhecida do **Safari/WebKit**, onde `compositionend` dispara *antes* de
`keydown`, fazendo `isComposing` já estar `false` no `keydown` que confirma
a composição (double-Enter). O Electron deste projeto roda **só sobre
Chromium** (Electron 43, `package.json`) — não existe superfície Safari nem
IE no runtime de produção. `event.nativeEvent.isComposing` sozinho é
suficiente e é o padrão usado pelo próprio React internamente para eventos
sintéticos. Confiança MEDIUM-HIGH — o comportamento do Chromium especificamente
(vs. Safari) é inferência a partir de várias fontes que isolam o bug como
"Safari-specific", não uma fonte que testa Electron/Chromium diretamente.
Se o plano quiser reduzir ainda mais o risco, o fallback custa uma linha
extra e não tem contraindicação: `!event.nativeEvent.isComposing &&
event.keyCode !== 229`.

**Isso é testável em vitest+jsdom sem IME real:** `KeyboardEvent` no jsdom
aceita a opção `isComposing` no construtor do evento (parte da spec), e
`@testing-library/react`'s `fireEvent.keyDown(el, { key: 'Enter',
isComposing: true })` repassa esse init dict — um teste automatizado pode
simular "Enter durante composição" sem precisar de um IME de verdade rodando
em Windows. Isso é diferente de "provar visualmente que funciona com um
teclado chinês/japonês/coreano real", que continua exigindo Windows +
pessoa (ver seção de acessibilidade abaixo).

## Don't Hand-Roll

| Problema | Não construir | Usar em vez disso | Por quê |
|---|---|---|---|
| Categoria recolhível | `useState` + altura animada manual | `Collapsible` (Radix, já em `node_modules/radix-ui`) | Gerencia estado aberto/fechado, animação de altura e `aria-expanded` de graça |
| Menu de contexto/dropdown | `onContextMenu` manual + `<div>` posicionado | `DropdownMenu`/`ContextMenu` (Radix) | Fecha ao clicar fora, navega por seta/Enter/Esc, `role="menu"` correto — reimplementar isso é a categoria clássica de bug de acessibilidade "parece funcionar, não funciona no teclado" |

| IME | Detectar CJK por regex no conteúdo digitado | `event.nativeEvent.isComposing` | O navegador já sabe exatamente quando uma composição está ativa — não há como replicar isso de forma confiável por heurística de texto |

instalável sem risco de versão (o `radix-ui` consolidado já traz os 3
primeiros). O trabalho real da fase é composição visual sobre eles, não
construção de mecanismo novo.

## Common Pitfalls

### Pitfall 1: CLI do shadcn escreve fora do lugar neste projeto especificamente
**O que dá errado:** arquivos gerados em `./@/components/ui/*.tsx` na raiz
do repo em vez de `src/renderer/src/components/ui/`.
**Por que acontece:** ausência de `vite.config.ts` na raiz (só existe
`electron.vite.config.ts`) — o CLI provavelmente não encontra o resolver de
alias esperado.
**Como evitar:** já não dá para evitar de origem sem mudar a estrutura do
projeto (fora de escopo); o procedimento é *detectar e corrigir* após cada
`add`, como já feito no Plano 03-01.
**Sinal de alerta:** `git status` mostrando um diretório `@/` na raiz do
repo depois de rodar `shadcn add`.

### Pitfall 2: tema escuro nunca aplicado
**O que dá errado:** toda a repaginação pode ser feita olhando os tokens
`.dark` no código sem nunca ver a tela real renderizar essas cores — porque
`.dark` nunca é aplicada.
**Por que acontece:** setup do `shadcn init` com `cssVariables: true` cria os
dois blocos de tema (`:root`/`.dark`), mas a aplicação da classe no HTML é
responsabilidade manual do app, não do CLI, e ninguém adicionou.
**Como evitar:** primeiro commit da fase deveria forçar `class="dark"` (ou
equivalente) e só then confiar em screenshots/verificação visual do resto.
**Sinal de alerta:** qualquer verificação visual que mostre fundo claro em
vez de "quase preto" (linguagem do brief).

### Pitfall 3: `sonner` traz `next-themes` de carona
**O que dá errado:** `npm install` de uma dependência (`next-themes`) que
não faz sentido num app Electron sem Next.js, só porque o template gerado
pelo CLI a importa.
**Como evitar:** editar o `sonner.tsx` gerado para remover o `useTheme()` e
fixar `theme="dark"` diretamente (ou ler a classe do `<html>` sem lib
externa), removendo `next-themes` do `package.json` antes de commitar.
**Sinal de alerta:** `next-themes` aparecendo em `package.json` após rodar o
`add`.

### Pitfall 4: testar acessibilidade "por leitura de código" em vez de execução
**O que dá errado:** declarar `aria-*`/foco visível como "feito" sem nunca
rodar nada, repetindo o padrão já visto no Plano 03-01 ("não foi verificado
visualmente por mim, apenas via análise estática").
**Como evitar:** ver seção "Acessibilidade e teclado em WSL2" abaixo — separar
explicitamente o que este ambiente consegue provar via teste automatizado
do que só uma pessoa com Windows + teclado consegue confirmar.
**Sinal de alerta:** um plano que marca ARIA/foco como "done" sem nenhum
teste rodado nem checkpoint humano listado.

## Acessibilidade e teclado em WSL2 — o que dá para provar aqui, o que não dá

**Ambiente atual:** `vitest.config.ts` define `environment: 'edge-runtime'`
globalmente (linha 5), usado hoje só para testes de `convex/*.test.ts`
(via `convex-test`) e funções puras em `src/renderer/src/lib/*.test.ts`.
**Nenhum dos 18 arquivos de teste hoje renderiza um componente React** — os
235 testes existentes são lógica pura (Convex, funções utilitárias). Não há
`jsdom`, `@testing-library/react`, nem `@testing-library/user-event`
instalados (`npm ls` confirma vazio).

**O que instalar, se a fase decidir cobrir isso por teste automatizado:**
```bash
npm install -D jsdom @testing-library/react @testing-library/user-event
```
`@testing-library/react@16.x+` suporta React 19 (`^18 || ^19` como peer,
confirmado via WebSearch/npm — versões anteriores, `14.x`, só suportavam
React 18). Isso **não precisa mudar o `vitest.config.ts` global** — vitest
1.6 (versão instalada, confirmada em `node_modules/vitest/package.json`)
suporta ambiente por arquivo via docblock `// @vitest-environment jsdom` no
topo do arquivo de teste, deixando `convex/*.test.ts` intocado em
`edge-runtime`. Custo: 3 pacotes novos, zero mudança de configuração global,
zero risco para os 235 testes já verdes.

**O que É verificável por teste automatizado (jsdom), sem tela real:**
- Foco programático: `element === document.activeElement` após `Tab`
  simulado via `userEvent.tab()`.
- `role`/`aria-*` presentes no DOM renderizado (`getByRole`,
  `toHaveAttribute`).
- Comportamento de teclado dentro de um componente isolado: `Enter`
  ativa um item de `DropdownMenu`, `Escape` fecha, seta move o item
  ativo — o Radix já expõe esse comportamento via eventos DOM padrão que
  jsdom simula corretamente.
- O guard de IME do composer (`isComposing: true` no evento sintético,
  já detalhado acima).
- Ordem de tabulação dentro de uma única região (ex.: dentro do rodapé de
  voz, dentro de um `DropdownMenu` aberto).

**O que NÃO é verificável sem Windows + pessoa:**
- Foco visível *de verdade* (contraste do anel de foco, se ele é cortado
  por `overflow:hidden` de algum container pai — jsdom não faz layout/
  pintura real).
- Navegação por Tab **entre regiões** da janela inteira (rail → sidebar →
  composer → membros) — depende de ordem real do DOM e de nenhum elemento
  interceptar o foco por acidente; jsdom não simula um documento inteiro
  sendo tabulado de ponta a ponta de forma confiável para esse tipo de
  teste de integração.
- Leitor de tela real (NVDA/Narrator) — jsdom não tem AT, só a árvore de
  acessibilidade "de papel".
- Redimensionamento real da janela do Electron no limite de 900px.

**Recomendação de corte:** cobrir por teste automatizado (jsdom) o
comportamento de teclado *dentro* de cada componente novo (menu, IME) no
mesmo plano que o introduz — é barato e já teria pego o bug do IME antes
deste research. Deixar para o checkpoint humano em Windows: navegação de
ponta a ponta por Tab entre as 4 regiões, foco visível real, e
redimensionamento da janela até 900×600. Isso seque a mesma lição do
`HANDOFF.md` nº 1 ("verificar no ambiente errado não é verificar") — jsdom
prova comportamento de componente, não prova a janela inteira.

## Corta-fácil: anexos e prévias de link — custo real, não design

### Anexos
Não existe nenhuma infraestrutura de arquivo hoje: `grep` por
`storage`/`generateUploadUrl`/`ctx.storage` em todo `convex/*.ts` não
retorna nada, e a tabela `messages` (`convex/schema.ts:55-60`) só tem
`channelId, authorId, content, createdAt` — nenhum campo de anexo.
`PROJECT.md:41` já lista "upload de arquivos" explicitamente como fora do
v1. Para existir de verdade (não só como "botão de clipe que não faz nada"),
precisaria: (1) mutation `generateUploadUrl` (API padrão do Convex File
Storage — `ctx.storage.generateUploadUrl()`, HIGH confidence por ser API
estável e documentada há anos, não verificada nesta sessão via Context7 mas
sem mudança conhecida); (2) campo novo em `messages` (`attachmentIds:
v.optional(v.array(v.id('_storage')))` ou tabela própria); (3) decisão de
limite de tamanho e o que acontece quando `ctx.storage.getUrl()` retorna
`null` (arquivo apagado/expirado). É mudança de schema + mutation + query —
exatamente o que o `CONTEXT.md` já identificou como não sendo trabalho de
UI.

### Prévias de link
Mesma conclusão, motivo diferente: buscar metadata (Open Graph/`<title>`) de
uma URL de terceiro exige uma requisição de rede saindo de algum lugar.
Três opções, cada uma com uma implicação de privacidade diferente que o
brief/CONTEXT já sinalizou como não decidida:
1. **Cliente de quem envia** busca a metadata antes de enviar a mensagem —
   o link é resolvido no computador do remetente (vaza o IP do remetente
   para o site linkado).
2. **Cliente de quem lê** busca ao renderizar — vaza o IP de **todo mundo**
   que abre o canal para o site linkado (pior para privacidade, mas mais
   simples de implementar sem backend).
3. **Convex** busca via `action` (única forma correta no Convex de fazer
   `fetch` para fora — `ctx.runAction` ou action HTTP direta, já que
   `action` roda em runtime Node/V8 com acesso a rede, diferente de
   `query`/`mutation`) — esconde o IP de todo mundo atrás do Convex, mas
   adiciona latência e um novo ponto de falha (site fora do ar, timeout,
   HTML malicioso).
Nenhuma das três é "só UI" — a primeira é a única que não toca `convex/`,
mas ainda assim precisa de uma função de parsing de HTML/meta tags no
renderer (nova dependência ou código próprio) e de um lugar para guardar o
resultado (cache local, já que refazer o fetch a cada render da mensagem
seria abusivo). Se os dois forem cortados, nenhum outro plano desta fase
depende deles (confirmado pela leitura de todos os componentes acima —
nenhum lugar do código atual referencia anexo ou embed).

function handleKeyDown(event: KeyboardEvent<HTMLTextAreaElement>): void {
  if (event.key === 'Enter' && !event.shiftKey && !event.nativeEvent.isComposing) {

  }

// @vitest-environment jsdom
import { fireEvent, render, screen } from '@testing-library/react'

test('Enter durante composição de IME não envia', () => {
