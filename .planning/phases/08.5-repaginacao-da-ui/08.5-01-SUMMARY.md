# Fase 8.5 Plano 01: Tema escuro e paleta — Summary

**O app deixa de renderizar no tema claro (`class="dark"` no `<html>`) e ganha a paleta que os próximos 8 planos consomem: um destaque em oklch ~264 ligado ao anel de foco, mais os pares `--success`/`--warning` no mesmo formato do `--destructive`.**

## Performance

- **Duração:** ~18 min
- **Tarefas:** 2 de 2
- **Arquivos modificados:** 2
- **Componentes tocados:** 0 (por desenho — as 15 ocorrências de cor direta pertencem aos planos donos daqueles arquivos)

## Accomplishments

- **O defeito que invalidava a fase inteira está corrigido.** `src/renderer/index.html`
  não tinha `class="dark"` e nada em `src/renderer/src` adicionava a classe, então
  `:root` (fundo `oklch(1 0 0)`, branco) vencia e toda a UI escrita da F3 à F8 para o
  escuro renderizava no claro. Achado de prioridade alta do `08.5-RESEARCH.md` e
  Pitfall 2 da fase.
- **A paleta existe e foi provada por build**, não por leitura: os oito utilitários
  novos aparecem no CSS gerado (ver "Verificação").
- **O anel de foco muda em toda a UI sem nenhum componente ser editado**: `@layer base`
  já aplica `outline-ring/50` a `*`, então bastou `--ring: var(--highlight)` no bloco
  `.dark`.
- **Documento declarado**: `lang="pt-BR"`, título `janja` (era "Electron") e
  `theme-color` `#0a0a0a`.

## A paleta — valores exatos e regra de uso

Os planos 03 a 09 vão citar esta seção ao trocar cor direta por token.

| Token | `:root` (claro, nunca usado) | `.dark` (o que o app usa) |
|---|---|---|
| `--highlight` | `oklch(0.52 0.2 264)` | `oklch(0.6 0.19 264)` |
| `--highlight-foreground` | `oklch(0.985 0 0)` | `oklch(0.985 0 0)` |
| `--success` | `oklch(0.55 0.15 150)` | `oklch(0.72 0.17 150)` |

| `--warning` | `oklch(0.62 0.14 85)` | `oklch(0.8 0.15 85)` |
| `--warning-foreground` | `oklch(0.145 0 0)` | `oklch(0.145 0 0)` |

E, no bloco `.dark`, `--ring: oklch(0.556 0 0)` virou `--ring: var(--highlight)`.
O `--ring` do `:root` ficou como estava.

**Regra do tom único (`--highlight`, matiz ~264 — a família do `--sidebar-primary`
órfão do boilerplate):** aparece em **estado ativo/selecionado**, **anel de foco** e
**marcador de não-lido**. Nunca como decoração. Não existe segundo tom de destaque.

**`--success` / `--warning` são significado, não destaque:** online, falando,
compartilhando, qualidade de conexão, reconectando. Não contam contra a regra acima.
Quem hoje usa `green-500`, `amber-500` ou `red-500` direto troca por
`bg-success`/`text-success`, `bg-warning`/`text-warning` e `bg-destructive`.

Utilitários que passaram a existir: `bg-`, `text-`, `ring-` e `border-` para
`highlight`, `success` e `warning`, mais os respectivos `-foreground`.

## O que NÃO foi verificado — e não podia ser

**Este ambiente é WSL2: sem Windows, sem tela e sem janela Electron renderizada.
Nenhum pixel foi pintado durante a execução deste plano. Eu não vi cor nenhuma, e
nenhuma afirmação sobre aparência aqui é observação — todas são consequência lógica do
CSS gerado.**

Fica para o checkpoint humano (Plano 08.5-17, em Windows nativo):

1. **O fundo está quase preto, não branco.** É o primeiro item do roteiro e o sinal de
   alerta do Pitfall 2. Se abrir branco, este plano falhou e o resto da fase está
   pintando no escuro.
2. **O tom de destaque tem contraste suficiente** contra `--background`
   (`oklch(0.145 0 0)`) e contra `--card` (`oklch(0.205 0 0)`). Os valores foram
   escolhidos no espaço OKLCH, não medidos numa tela.
3. **O anel de foco é visível e não é cortado** por `overflow: hidden` de algum
   container — jsdom não pinta e WSL2 não tem tela. Vale checar em item de sidebar,
   botão do rail e campo do composer.
4. **O título da janela mostra "janja"** na barra do Windows e na barra de tarefas.
5. **Não há flash de tema claro no boot.** Como a classe está no HTML e não em JS, não
   deveria haver — mas quem confirma é o olho.

## Decisions Made

- **Classe no HTML, não em JS.** Sem alternância de tema no produto, um
  `document.documentElement.classList.add('dark')` no boot só acrescentaria um flash de
  tema claro e mais um lugar para alguém esquecer. Decisão já travada no
  `08.5-CONTEXT.md`, aqui só registrada.
- **O bloco `:root` ganhou os tokens mesmo o app nunca o usando.** Bloco de tema pela
  metade é a próxima armadilha para quem abrir este arquivo daqui a seis meses.
- **Nenhum token órfão foi removido** (`--sidebar-primary`, `--chart-*`): são
  boilerplate do `shadcn init`, não fazem mal, e apagá-los é ruído de diff num arquivo
  que outros 8 planos vão ler.

## Deviations from Plan

Duas correções pequenas, nenhuma arquitetural. Nenhuma alterou o comportamento previsto.

**1. [Rule 1 — verificação incorreta no próprio plano] `grep -c "connect-src"` retorna 2, não 1**

- **Encontrado em:** Task 1, ao rodar a verificação escrita no plano.
- **Problema:** o plano manda conferir que `grep -c "connect-src"` continua retornando
  1 como prova de CSP intacta. Só que o HEAD anterior **já retornava 2**: a string
  aparece no atributo `content` da meta e outra vez no comentário que documenta a CSP
  (`connect-src: Convex (dados) e LiveKit...`). O critério estava errado, não o arquivo.
- **Correção:** a CSP foi provada intacta por um critério mais forte —
  `git show HEAD:src/renderer/index.html | grep -c connect-src` também retorna 2, e
  `git diff src/renderer/index.html | grep "Content-Security\|default-src"` não retorna
  **nenhuma** linha alterada. O bloco de CSP está byte a byte igual.
- **Impacto:** nenhum no código. Os planos seguintes que copiarem esse verify devem
  esperar 2.

**2. [Rule 3 — bloqueio de formatação] `main.css` não é prettier-clean no HEAD**

- **Encontrado em:** Task 2, ao rodar `npx prettier --check`.
- **Problema:** rodar o prettier no arquivo reescreveu duas linhas que eu não toquei
  (`@import "tailwindcss"` → `@import 'tailwindcss'`). O arquivo **já era**
  não-conformante antes da minha edição — confirmado com
  `git show HEAD:...main.css | npx prettier --stdin-filepath ... --check`, que também
  acusa. Não é regressão minha.
- **Correção:** as duas linhas de `@import` foram devolvidas ao formato original. O
  diff do commit contém **só** os tokens novos. O prettier não é gate de build nem de
  CI aqui (`npm run lint` é eslint puro), e diff limpo vale mais num arquivo que outros
  8 planos vão abrir. `index.html`, esse sim, passa no `prettier --check`.
- **Follow-up para o orquestrador:** existe uma divergência de formatação
  pré-existente entre o `main.css` e a config do prettier do repo. Se for para
  normalizar, que seja num commit `style:` próprio, não escondido dentro de um plano de
  UI.

**Melhoria além do texto do plano (sem desvio de escopo):** o plano mandava provar os
tokens com `npm run build` + `grep` no CSS-fonte. Isso não prova utilitário nenhum —
Tailwind v4 só emite a classe se ela aparecer no código escaneado. Foi feito o build
com arquivo-sonda descrito acima, apagado antes do commit. Também foi comprimido o
comentário duplicado: o racional completo fica uma vez no `:root` e o bloco `.dark`
traz uma referência de duas linhas, em vez do mesmo parágrafo colado duas vezes.
