## (a) O CLI do shadcn escreveu em `./@/` de novo? SIM — nas duas invocações

Pitfall 1 do RESEARCH confirmado pela terceira vez neste projeto. Saída literal:


alias. Procedimento aplicado: `mv` de cada arquivo para
`src/renderer/src/components/ui/`, `find @ -type f` conferido **vazio** antes de apagar, e
`rm -rf @`. Estado final: `test ! -d @` passa.

acontece toda vez. Conte com o passo de mover.

## (b) Comportamentos de teclado: os 4 são observáveis em jsdom

Os quatro comportamentos que o plano listou como incertos **funcionam todos**. Nenhuma
asserção precisou ser removida, e ainda coube uma quinta. Os planos 05, 06, 07 e 09 podem
prometer prova de teclado com segurança.

| # | Comportamento | Observável? | Como asseverar |
|---|---|---|---|
| 1 | `Tab` leva o foco ao gatilho | **Sim** | `document.activeElement === gatilho`; `aria-haspopup="menu"`, `aria-expanded="false"` |
| 2 | `{Enter}` abre o menu | **Sim** | `getAllByRole('menuitem')` acha 2; `aria-expanded="true"`; o foco vai para o **primeiro item**, não fica no gatilho |
| 3 | `{ArrowDown}` move o item ativo | **Sim, pelos dois sinais** | `document.activeElement === segundoItem` **e** `data-highlighted` presente no 2º (string vazia) / `null` no 1º |
| 4 | `{Escape}` fecha e devolve o foco | **Sim** | 0 `menuitem` no DOM, `aria-expanded="false"`, `document.activeElement === gatilho` |
| 5 (extra) | `{Enter}` num item dispara `onSelect` e fecha | **Sim** | callback registrou `['segundo']` e o menu sumiu |

Descobertas adicionais que economizam tempo de quem for escrever o próximo teste:

- **`Select` também abre por `{Enter}` e expõe `role="option"`** — testável do mesmo jeito.
  (Descoberto ao investigar um falso negativo, ver abaixo.)
- **Clique de mouse no `DropdownMenu` funciona sem polyfill nenhum.** Se um teste de menu
  falhar, não é o pointer.
- **`afterEach(cleanup)` é obrigatório e a falta dele produz um erro que engana.** O vitest
  aqui não roda com `globals: true`, então a limpeza automática do
  `@testing-library/react` **não se registra**. Sem ela, o render do teste anterior
  continua no `document` e `user.tab()` foca o gatilho do teste passado — foi exatamente
  assim que um `Select` "não abriu" numa sonda minha, quando na verdade eu estava
  digitando num botão de outro teste. Quem copiar o padrão, copie o `afterEach`.

### O `jsdom-setup.ts` é necessário? Sim — e foi provado, não assumido

O teste do `DropdownMenu` **passa mesmo sem importar o setup**: o caminho de teclado do
menu nunca toca nas APIs que faltam. Isso poderia sugerir que o arquivo é enfeite. Não é.
O jsdom 29.1.1 não implementa **nenhuma** delas (medido, não suposto):

```
hasPointerCapture: undefined   setPointerCapture: undefined
releasePointerCapture: undefined   scrollIntoView: undefined
ResizeObserver: undefined   IntersectionObserver: undefined   matchMedia: undefined
```

E a prova direta, com `ScrollArea` (componente que está espalhado por toda a UI desta fase):

```
### SEM SETUP ###   ReferenceError: ResizeObserver is not defined   -> 1 failed | 1 passed
### COM SETUP ###   Test Files 1 passed (1)   Tests 2 passed (2)
```

**Regra prática:** importe `@/test/jsdom-setup` em todo teste de componente. Custa uma
linha e evita meia hora perdida atrás de um `ReferenceError` que não menciona o seu
componente.

Duas lacunas conhecidas do setup, para quem esbarrar nelas: `IntersectionObserver` e
`matchMedia` continuam ausentes (nenhum componente atual precisou). Se um plano precisar,
acrescente no mesmo arquivo, no mesmo formato defensivo.

## Deviations from Plan

### 1. [Rule 3 — bloqueio] `vitest.config.ts` PRECISOU mudar: alias `@/`

- **Encontrado em:** Task 3, na primeira execução do teste.
- **Erro literal:** `Failed to resolve import "@/test/jsdom-setup" from ".../dropdown-menu.test.tsx". Does the file exist?`
- **Por que não dava para contornar com import relativo:** o problema não é o import do
  teste. É que **`dropdown-menu.tsx` importa `@/lib/utils`** (como todos os 14 componentes
  de `ui/`). O alias `@` só existe no bloco `renderer` do `electron.vite.config.ts`, que o
  vitest não lê. Sem alias, **nenhum teste de componente é possível neste repo**, com
  import relativo ou sem.
- **Correção:** `resolve.alias` acrescentado ao `vitest.config.ts`, espelhando o
  `electron.vite.config.ts` (`@` e `@renderer` → `src/renderer/src`), com comentário
  explicando por que está duplicado.
- **Por que isto não viola a intenção do plano:** o plano proíbe mudar o `vitest.config.ts`
  para proteger `environment: 'edge-runtime'`, do qual o `convex-test` depende. O bloco
  `test{}` **não foi tocado** — a mudança é aditiva, fora dele. Os 10 arquivos de teste de
  `convex/` continuam passando, que é a prova que o plano pedia.
- **Consequência para o verify do plano:** `git diff --stat vitest.config.ts` **não** está
  vazio (`1 file changed, 15 insertions(+)`). Esse critério do plano não podia ser
  satisfeito junto com "escrever um teste de componente".
- **Commit:** `d3167d7`

### 2. [Rule 1 — asserção que não existe] `toHaveAttribute` não funciona sem `jest-dom`

- **Encontrado em:** Task 3. Primeira versão do teste usava `expect(el).toHaveAttribute(...)`
  e 3 dos 5 testes quebraram com `Invalid Chai property: toHaveAttribute`.
- **Causa:** esse matcher vem de `@testing-library/jest-dom`, que o plano decidiu **não**
  instalar. Erro meu, não do plano.
- **Correção:** trocado por `expect(el.getAttribute('aria-expanded')).toBe('false')` etc.
  O arquivo ganhou um comentário avisando disso, para que os planos 05 e 09 não repitam.

### 3. [Documentado, não corrigido] `eslint` acusa os arquivos gerados pelo shadcn

- `npx eslint` nos dois componentes novos aponta 18 erros de
  `@typescript-eslint/explicit-function-return-type`. **Não é regressão:** o
  `popover.tsx`, que já estava no repo, tem 7 erros da mesma regra, e o `npm run lint` do
  HEAD anterior já retornava 99 erros no projeto todo.
- **Decisão:** não editar os arquivos gerados. O plano manda seguir literalmente o estilo
  dos 12 existentes, `npm run lint` não é gate (`npm run build` = typecheck + electron-vite)
  e divergir do template do shadcn dificultaria a próxima atualização.
- **Follow-up para o orquestrador:** se for para tornar o lint verde, que seja num plano
  `chore:` próprio, com decisão explícita sobre desativar a regra em `components/ui/**`.

**Sobre os arquivos gerados terem sido commitados verbatim:** `dropdown-menu.tsx` traz
`"use client"` (diretiva de Next, inócua aqui) e `collapsible.tsx` usa
`React.ComponentProps` **sem importar React**. Os dois foram mantidos porque combinam com
o que já existe: `tooltip.tsx` e `slider.tsx` também têm `"use client"`, e
`dialog.tsx`/`input.tsx`/`textarea.tsx` também usam `React.*` sem import (funciona: em
posição de tipo, o namespace UMD do `@types/react` resolve). `npm run typecheck` passa.
