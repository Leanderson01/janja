# Fase 8.5 Plano 13: Anexos no backend — Summary

**A tabela `messages` passa a carregar anexos opcionais, a URL de upload só sai
para quem é membro do canal, e o tamanho do arquivo é lido do `_storage` pelo
servidor — o cliente nunca declara quanto o arquivo pesa.**

## Performance

- **Duração:** ~25 min
- **Tarefas:** 3 de 3
- **Arquivos modificados:** 3

## Realizações

- `messages.attachments`: `v.optional(v.array(v.object({ storageId, name, size, contentType? })))`.
- `generateUploadUrl(channelId)`: exige `requireChannelMembership` e canal de texto antes de emitir a URL.
- `sendMessage`: aceita `attachments: [{ storageId, name }]`, resolve `size`/`contentType` via
  `ctx.db.system.get('_storage', storageId)`, aplica os dois limites e só então insere.
- `listMessages`: cada anexo sai enriquecido com `url` (`ctx.storage.getUrl`), `null` quando o arquivo sumiu.
- 15 testes novos em `convex/messages.test.ts` (10 → 25 no arquivo).

## O limite escolhido, e por quê

| Constante | Valor | Motivo |
|---|---|---|
| `MAX_ATTACHMENT_BYTES` | 25 MB (`25 * 1024 * 1024`) | Mesmo teto do Discord gratuito: o grupo já conhece esse número, então "não passou" não vira surpresa. Grande o bastante para print, log e clipe curto — o uso real do grupo. |
| `MAX_ATTACHMENTS_PER_MESSAGE` | 5 | Dá teto ao custo de leitura: `listMessages` faz um `getUrl` por anexo, por mensagem, por página. |

O teto é **inclusivo**: exatamente 25 MB passa, 25 MB + 1 byte é recusado (os dois casos têm teste).

**Onde o limite é aplicado:** no servidor, dentro de `sendMessage`, sobre o `size` lido do `_storage`.
O cliente nem manda `size` — se mandasse, o limite seria contornável com `size: 1`. A checagem do
cliente (Plano 08.5-14) existe só para poupar upload inútil; quem decide é esta.

**Risco conhecido e aceito:** o plano gratuito do Convex tem cota finita de file storage. Vinte
pessoas mandando vídeo de 25 MB consomem essa cota rápido. Não há cota por usuário nem expurgo
automático — seria feature nova, não anexo. Registrado aqui para não virar surpresa de fatura.

## As três perguntas que o CONTEXT.md deixou em aberto

1. **Falha no meio do upload** — o arquivo pode chegar ao storage sem que `sendMessage` aconteça
   (o app fecha, a rede cai). O resultado é um arquivo órfão: ocupa cota e nunca aparece para
   ninguém, porque só existe linha no banco depois que `sendMessage` valida. Não há coleta
   automática de órfãos nesta fase.
2. **`storageId` que não existe** (inventado pelo cliente, ou apagado entre o upload e o envio) —
   `sendMessage` recusa com "Arquivo não encontrado no armazenamento" e **nada é inserido**.
3. **Arquivo que some depois de a mensagem existir** — `listMessages` devolve `url: null` e o resto
   do anexo intacto (`name`, `size`). Não é erro e não quebra a listagem; a UI do Plano 08.5-14
   mostra "arquivo indisponível" em vez de imagem quebrada. Tem teste.

## Escopo respeitado

- **Só canal de servidor.** `dmMessages` não foi tocada — decisão registrada no CONTEXT.md.
- **Sem cargos.** A única autorização é `requireChannelMembership`, exatamente como no resto da Fase 4.
- **Canal de voz não aceita anexo**, pelo mesmo motivo de não aceitar mensagem.

## O que o `convex-test` conseguiu emular (mais do que o plano supunha)

Conferido lendo `node_modules/convex-test/dist/index.js` (v0.0.55), não de memória:

| API | Emulada? | Consequência nos testes |
|---|---|---|
| `ctx.storage.store(blob)` em `t.run` | Sim (`storage/storeBlob`, insere em `_storage` com `size` e `sha256`) | Arquivos de verdade, inclusive um de 25 MB e outro de 25 MB + 1 byte |
| `ctx.storage.getUrl(id)` | Sim (`1.0/storageGetUrl`) — URL falsa, `null` quando o arquivo não existe | O caso "arquivo sumiu → url null" é testado de verdade |
| `ctx.storage.delete(id)` | Sim (`1.0/storageDelete`) | Dá um `Id<'_storage'>` de formato válido cujo arquivo não existe |
| `ctx.db.system.get('_storage', id)` | Sim | O caminho de leitura de metadados é o real |
| `ctx.storage.generateUploadUrl()` | Sim, mas devolve URL falsa | Só dá para afirmar que só membro recebe uma string. **O POST do arquivo nessa URL não existe no harness.** |
| `contentType` | **Não** — o harness insere só `size` e `sha256` em `_storage` | Nenhum teste afirma nada sobre `contentType`; a propagação dele é pendência de verificação humana |

Por isso o teste de tamanho **não** virou mock: ele grava um Blob de 26.214.401 bytes e deixa o
servidor ler o tamanho real. Custo: ~2,9 s do tempo do arquivo de teste, quase tudo em sha256.

não herdado da pesquisa:

## Desvios do plano

Nenhum desvio de comportamento. Três precisões que o plano deixou em aberto e foram decididas aqui:

1. **O teto de 25 MB é inclusivo** (`size > MAX` recusa). O plano não dizia se 25 MB exatos passavam;
   ambos os lados da fronteira ganharam teste.
2. **`content` acima de 2000 caracteres continua recusado mesmo com anexo.** O plano dizia que o teto
   "não muda"; a checagem foi separada em duas para que a presença de anexo relaxe só o mínimo, nunca o máximo.
3. **O plano previa que talvez o storage não fosse emulado.** Ele é. Os testes de tamanho e de
   `url: null`, que o plano mandava adiar para verificação humana caso não houvesse emulação,
   existem e passam — sem mock.

## `convex/_generated`: nada foi escrito à mão

`api.d.ts` mapeia o módulo inteiro (`messages: typeof messages`), não função por função. Como
`generateUploadUrl` é um export novo de um arquivo que já existia — e nenhum arquivo novo foi criado
em `convex/` — a entrada existente já cobre. Verificado com um arquivo-sonda temporário que referencia
`api.messages.generateUploadUrl` e passa no `tsc -p tsconfig.convex.json` (sonda apagada em seguida,
não commitada). **Zero linhas manuais em `_generated`.**

## O que SÓ pode ser verificado depois do `npx convex dev` no Windows

O push do Convex é impossível nesta máquina: o token em `~/.convex/config.json` é de outra conta
(`npx convex dev --once` → "You don't have access to the selected project"). Nada abaixo foi provado:

1. **Que o deployment aceita o schema novo** — a validação dos documentos já gravados contra o
   `messages` com `attachments` só acontece no push. (O campo é opcional exatamente para isso.)
2. **Que uma URL de upload real funciona** — que o POST devolve `{ storageId }` e que esse id é
   aceito por `sendMessage`. O harness devolve URL falsa; não há servidor do outro lado.
3. **Que `contentType` chega ao banco** — o storage real preenche `contentType` a partir do upload,
   o harness não. É o único campo do anexo sem cobertura.
4. **Que a URL de `getUrl` abre o arquivo no cliente** — no harness ela é uma string sintética.
5. **Comportamento e tempo de um arquivo de 25 MB de verdade** subindo por rede doméstica, e o
   consumo de cota que isso gera.
6. **Que o bundler do Convex aceita o módulo** — lição nº 1 do HANDOFF.md: passar sob vitest
   (edge-runtime) não prova que passa sob o bundler do Convex. Aqui não há dependência nova, o que
   torna o risco baixo, mas não zero.

Tudo isso é o primeiro bloco do roteiro do Plano 08.5-17, cujo primeiro passo obrigatório é o Leo
dar `git pull` no Windows e rodar `npx convex dev --once` — que também regenera `convex/_generated/`.
