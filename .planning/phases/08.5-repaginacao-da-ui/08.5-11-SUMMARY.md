### 2. A fórmula antiga e a nova são a MESMA fórmula para quem não ajustou ninguém

A fórmula antiga era `deafened ? 0 : 1`. A nova é `effectiveVolume(pref, deafened)`.
`janja:participant-volumes` é uma chave nova de `localStorage`: **todo usuário existente
começa com o mapa vazio**, ou seja `pref === undefined` para todo mundo. Executado, não
argumentado:

```ts
const formulaAntiga = (deafened: boolean): number => (deafened ? 0 : 1)
for (const deafened of [true, false])
  expect(effectiveVolume(undefined, deafened)).toBe(formulaAntiga(deafened))
```

```
 ✓ o ensurdecimento nao regrediu (3 tests)
   ✓ sem preferencia nenhuma, a nova regra devolve exatamente o que a antiga devolvia
   ✓ mesmo COM preferencia, ensurdecido continua zerando tudo
   ✓ nao-ensurdecido sem preferencia toca no volume cheio, como antes
```

(Arquivo temporário, rodado e apagado na mesma linha de comando — `files_modified` não tem
vaga para ele. As mesmas asserções vivem, permanentes, em `participant-volumes.test.ts`:
`effectiveVolume(undefined, true) === 0`, `effectiveVolume(undefined, false) === 1`, e a
tabela completa com `{volume: 2, silenced: true/false}` × ensurdecido → sempre 0.)

### 3. A estrutura do efeito é a mesma, no lugar novo

| Antes (`VoiceControlBar`) | Depois (`voice-context`) |
|---|---|
| varre `room.remoteParticipants` → `audioTrackPublications` | idem, mesma coleção |
| `if (publication.track) applyVolume(...)` | idem |
| `isAudioTrack(track)` como guarda | idem |
| escuta `RoomEvent.TrackSubscribed` | idem |
| `room.off` no cleanup | idem |
| deps `[deafened, room]` | `[participantVolumes, deafened, room]` |

A única diferença estrutural é a dependência a mais — e é por causa dela que `deafened`
precisou virar **estado**: um `ref` não reexecuta efeito nenhum. `deafenedRef` continua
existindo (é lido de dentro de callbacks assíncronos da fila de transições, onde uma
closure sobre o estado estaria velha) e passou a ser espelho, escrito pelo mesmo
`setDeafened`.

### 4. A ordem entre `attach()` e `setVolume` está preservada

`setVolume` só tem efeito sobre elementos já criados por `attach()` — está escrito no
comentário do efeito de áudio remoto desde o Plano 07-05, e antes deste plano os dois
moravam em componentes diferentes. Agora moram no mesmo arquivo, e a ordem é garantida
por construção:

- o efeito de `attach` é **declarado antes**, então seu listener de `TrackSubscribed` é
  registrado antes e roda primeiro no mesmo evento;
- o de `attach` tem deps `[room]` e **nunca se reinscreve**, enquanto o de volume se
  reinscreve a cada mudança de preferência — o que só o empurra para mais tarde na fila de
  listeners, nunca para antes.

O efeito de `attach` **não foi tocado** (é o que o plano manda explicitamente):

## (b) A DECISÃO QUE PRECISA DO USUÁRIO: 200% não existe hoje

O plano pede slider de **0 a 200%**, "o dobro, como o Discord permite". **Não é possível
sem uma mudança arquitetural**, e a razão foi verificada no pacote instalado, não lembrada:

```
$ node_modules/livekit-client/dist/livekit-client.esm.mjs:28461
  setVolume(volume) {
    for (const el of this.attachedElements) {
      if (this.audioContext) {
        this.gainNode?.gain.setTargetAtTime(volume, 0, 0.1);   // caminho Web Audio
      } else {
        el.volume = volume;                                     // <- o nosso caminho
      }
    }
```

- `webAudioMix` **default é `false`** no `livekit-client` 2.22
  (`livekit-client.esm.mjs:19357`), e este projeto faz `new Room()` **sem opções**;
- o `audioContext` só chega ao `RemoteAudioTrack` se `webAudioMix` for verdadeiro
  (`acquireAudioContext`: `if (this.options.webAudioMix) remoteParticipants.forEach(p =>
  p.setAudioContext(...))`) — verificado no bundle;
- portanto `setVolume(v)` executa `el.volume = v`, e **`HTMLMediaElement.volume` lança
  `IndexSizeError` para qualquer valor fora de 0..1**.

Ou seja: um `1.5` escapando para lá **não "não faria nada"** — derrubaria a passada que
aplica o volume, e com ela o **ensurdecimento dos participantes seguintes daquela varredura**.
Exatamente a regressão que este plano existe para impedir.

**O que foi feito:** `MAX_PLAYBACK_VOLUME = 1`, o slider vai a 100%, e `effectiveVolume`
grampeia antes de entregar ao SDK (com teste dedicado: "nunca devolve valor que o
HTMLMediaElement recusaria"). O **armazenamento** continua aceitando 0..2, como o plano
escreveu — é headroom, não uso.

**O que fica para o usuário decidir** (e por que não foi decidido aqui): habilitar
`webAudioMix: true` no `new Room()` liga o caminho do `GainNode` e o volume acima de 100%
passa a funcionar. Só que isso:

1. **muta deliberadamente** os elementos `<audio>` e roteia o som pelo `AudioContext`
   (`attach()`: `element.volume = 0; element.muted = true`);
2. **muda o caminho de `switchActiveDevice('audiooutput', ...)`** — VOICE-20, o seletor de
   dispositivo de saída do Plano 07-05 —, que passa a depender de `setSinkId` no
   `AudioContext` e **lança** onde ele não existe (`livekit-client.esm.mjs:33184`);
3. mexeria na reprodução de **toda** a call, no meio de uma fase de UI, com três
   checkpoints de voz ainda pendentes.

Isso é mudança arquitetural sobre o contrato de mídia da Fase 7 — **PARADO e reportado, não
feito**. Quando/se for aprovado, o custo do lado deste plano é **uma constante**
(`MAX_PLAYBACK_VOLUME`), e ela já está documentada no arquivo apontando para cá.

## (c) O que foi entregue, tarefa a tarefa

### Task 1 — `lib/participant-volumes.ts` (178 linhas) + 35 testes

Mesmo padrão defensivo de `voice-preferences.ts` (07-05) e `screenshare-preferences.ts`
(08-05), com a mesma justificativa de **estado de MÁQUINA**: o volume que você dá para o
microfone estourado do fulano é do SEU computador, com o SEU fone. Nunca vai para o Convex.

- `STORAGE_KEY = 'janja:participant-volumes'`, chave do mapa = `identity` do LiveKit =
  `users._id`;
- `loadParticipantVolumes()` / `saveParticipantVolumes(map)` — nunca lançam (storage
  ausente, JSON quebrado, quota, `getItem` que explode);
- `sanitize`: descarta chaves cujo valor não é objeto, grampeia `volume` em 0..2, `silenced`
  não-booleano vira `false`, array/escalar no topo vira mapa vazio;
- **poda ao salvar**: entrada em volume 1 e não silenciada não é guardada — `effectiveVolume
  (undefined, ...)` devolve exatamente o mesmo, e guardar o padrão para 200 pessoas é lixo
  que cresce sozinho. Voltar alguém ao volume normal **apaga** a entrada dele;
- `effectiveVolume(pref, deafened)` — a regra central, pura: **ensurdecido → 0**;
  **silenciado → 0**; senão o volume, grampeado no teto de reprodução.

Os testes cobrem round-trip, storage ausente (que é o estado **nativo** do `edge-runtime`,
o mesmo achado do 08-05), 6 formas de corrupção, limites, poda, e a tabela inteira de
precedência — incluindo uma varredura de 32 combinações provando que o resultado é sempre
um número que o `HTMLMediaElement` aceita.

### Task 2 — a centralização

Em `voice-context.tsx`:

- `deafened` virou **estado** (com `deafenedRef` como espelho síncrono, escrito pelo mesmo
  `setDeafened`);
- `participantVolumes` é estado carregado do `localStorage` no inicializador preguiçoso,
  com um `participantVolumesRef` espelho — os handlers precisam ler o mapa atual para
  escrever o próximo, e fazer isso dentro do updater de `setState` significaria gravar no
  `localStorage` de dentro dele, que com **`StrictMode` ligado** (main.tsx) roda duas vezes;
- `setParticipantVolume(identity, volume)` e `toggleParticipantSilenced(identity)` gravam
  na hora e publicam o mapa **já podado** (o que a UI lê é literalmente o que ficou salvo);
- um efeito só aplica `effectiveVolume` a toda track de áudio remota e ao que chega depois.

`participant.audioTrackPublications` cobre microfone **e** áudio de sistema do
compartilhamento de tela da mesma pessoa (SHARE-03) — desejado: silenciar o fulano silencia
o fulano inteiro.

### Task 3 — o menu no palco

Cada ladrilho da grade de **outra** pessoa, no canal conectado, virou gatilho de
`DropdownMenu` controlado — mesmo padrão único da fase (Plano 08.5-02/08.5-04): abre por
clique, por `Enter` no `<button>` e por `onContextMenu` no mesmo elemento, sem
`context-menu` do Radix.

Conteúdo: nome da pessoa (`DropdownMenuLabel`), slider de volume 0-100% passo 5 com o valor
numérico ao lado e `aria-label="Volume de {nome}"`, dois itens de teclado, e
**"Silenciar para mim" / "Ouvir de novo"**.

**"para mim" é obrigatório no rótulo e não é preciosismo:** sem essas duas palavras o
usuário acredita que mutou a pessoa para a call inteira. Isso seria **moderação** — coisa de
cargo, que não existe neste app e está fora desta fase.

**Estado visível**, porque silenciar sem sinal vira "sumiu da call": avatar em `opacity-60`
+ badge `VolumeX` no canto superior esquerdo (o inferior direito é do mute, que é da
**pessoa**; os dois significam coisas diferentes e não podem se sobrepor). E — acréscimo,
mesmo argumento — a **porcentagem ao lado do nome** quando o volume foi baixado: volume
esquecido em 20% é indistinguível de "essa pessoa fala baixo".

**Sem menu** para mim mesmo (não me ouço) e em canal apenas **visualizado** (prévia: não há
track tocando, e o menu prometeria um efeito que não aconteceria). Nesses casos o ladrilho
volta a ser exatamente o `<div>` de antes — nenhuma semântica de botão para quem não tem
ação.

**Volume NÃO foi duplicado na `MemberList`** (Plano 08.5-04), como o plano manda registrar:
a lista de membros é do servidor inteiro, inclusive de quem não está em call nenhuma, e
volume só faz sentido para quem está tocando áudio agora.

## Deviations from Plan

### 1. [Rule 1 — bug que o plano teria introduzido] Teto de 100%, não 200%

Descrito por inteiro na seção (b). O plano pede 0..200%; entregar isso com a configuração
atual do `Room` faria `setVolume` lançar `IndexSizeError` e derrubar a aplicação do volume
**e do ensurdecimento**. Corrigido com `MAX_PLAYBACK_VOLUME = 1` + slider até 100% + teste
que trava o invariante. **A parte arquitetural (`webAudioMix: true`) foi PARADA e está no
retorno para o usuário decidir**, não implementada.

### 2. [Rule 3 — impossibilidade estrutural] Menu só na grade, não na faixa

- **O plano diz:** "Cada participante do palco (ladrilho da grade E item da faixa, que o
  Plano 08.5-07 unificou num componente só)".
- **O código diz outra coisa:** o 08.5-07 **não** unificou os dois. A grade
  (`VoiceParticipantGrid`) está em `CallStage.tsx`; a faixa (`ParticipantStrip`) está em
  `ParticipantStrip.tsx`, arquivo próprio. O que foi compartilhado foram três símbolos
  (`initialsFor`, `ConnectionQualityIcon`, `useVoiceParticipants`), como o próprio
  08.5-07-SUMMARY registra.
- **Por que não estendi para a faixa:** `ParticipantStrip.tsx` **não está no
  `files_modified`** deste plano, e outros dois executores rodam nesta árvore agora. É
  exatamente a lição nº 6 do HANDOFF.
- **Consequência real, e ela é de usabilidade:** no layout `share` (compartilhamento
  ocupando o palco) a grade fica com `hidden` e **só a faixa aparece** — nesse layout o menu
  de volume fica inalcançável. O contorno existe e é de um clique: "Ocultar tela"
  (`EyeOff`) volta para `tiles`, ajusta, "Mostrar tela" (`Eye`) volta. Mas é contorno.
- **Correção recomendada, barata e mecânica:** extrair `ParticipantTile` (ou só o
  `DropdownMenuContent`) de `CallStage.tsx` para um arquivo próprio e consumi-lo nos dois —
  respeitando a direção única de importação do 08.5-07. Fica para quem consolidar a fase,
  com os dois arquivos na mesma lista.

### 3. [Rule 2 — acessibilidade que não podia depender de um palpite] Slider **e** dois itens de teclado

O plano prevê a troca ("se não for possível fazer o slider funcionar por teclado dentro do
menu, trocar por dois itens... e registrar a troca") e manda **testar rodando**. Rodar é
justamente o que não existe aqui: WSL2, sem janela, sem tela. E `CallStage.test.tsx` não
está no `files_modified`, então nem o teste em jsdom era uma opção.

Entreguei **os dois**: o slider (numa área **não-item**, com `stopPropagation` no
`onKeyDown` e no `onPointerDown`, que é o cuidado que o plano descreve) **e** os itens
"Aumentar volume"/"Diminuir volume", passo de 10%, com `event.preventDefault()` no
`onSelect` para o menu não fechar a cada passo. Os dois escrevem no mesmo lugar.

**Por quê:** um controle contínuo dentro de um menu do Radix pode ou não receber as setas —
e um controle possivelmente inalcançável por teclado não podia ser o **único** caminho.
Custou ~15 linhas. **No checkpoint humano isso vira decisão de uma linha:** se o slider
responder bem ao teclado, os dois itens saem; se não responder, o slider sai e os itens
ficam. Nenhum dos dois é carga permanente.

### 4. [Rule 1 — bug que a mudança teria introduzido] Onde o ensurdecer é resetado

Com `deafened` morando no provider, manter o reset onde ele estava (durante a renderização
do `VoiceControlBar`, no bloco de troca de canal) seria chamar o setter de **outro**
componente durante o render — o "Cannot update a component while rendering a different
component" do React. O reset foi para `voice-context.tsx`, no join bem-sucedido, **onde
`deafenedRef.current = false` já morava desde o Plano 07-11**, agora via `setDeafened(false)`
para os dois andarem juntos.

**Efeito colateral, e ele é uma melhora:** antes, o ícone do rodapé zerava na troca de
**intenção** e o `deafenedRef` só zerava no **join bem-sucedido** — um join que falhasse
deixava o botão dizendo "não ensurdecido" com a reprodução ainda ensurdecida. Agora os dois
zeram no mesmo instante. O custo é o ícone só destravar quando o join conclui; nesse
intervalo o botão está `disabled={!isReady}` de qualquer forma.

### 5. [Registro] O comentário sem a palavra literal

O comentário que explica a saída do efeito no `VoiceControlBar` foi escrito **sem** a string
`setVolume`, para que o `grep` do plano bata em zero de verdade. Mesmo cuidado que o Plano
08.5-09 tomou com `space-y-` e mesmo tipo de falso positivo que o 08.5-07 registrou com
`grep -c "attach()"`.

### 6. [Risco assumido, e não repetir] Um `git stash` de 2 segundos

Para provar que o erro de `react-refresh` em `voice-context.tsx` era **pré-existente**, rodei
`git stash` → `eslint` → `git stash pop`. Funcionou (`git status` depois mostrou só os meus
2 arquivos modificados, `git stash list` vazio), mas foi **imprudente com dois executores na
mesma árvore**: o stash pega o trabalho não-commitado de todo mundo. Registrado para não se
repetir — o certo era `git show HEAD:arquivo > /tmp/x.tsx && eslint /tmp/x.tsx`.

**Total:** 3 auto-corrigidos (2× Rule 1, 1× Rule 2), 1 impossibilidade estrutural
contornada e documentada (Rule 3), 2 registros. **Uma mudança arquitetural identificada e
PARADA** (`webAudioMix`), levada ao usuário em vez de decidida aqui.

## O que NÃO foi verificado — e não podia ser

**Ambiente WSL2: sem Windows, sem tela, sem janela Electron, sem dispositivo de áudio e sem
segunda pessoa. EU NÃO OUVI VOLUME NENHUM. Nenhum pixel foi renderizado e nenhum decibel foi
produzido durante esta execução.** Esta é uma feature cujo resultado final é **audível**, e a
única parte dela que dá para provar aqui é a aritmética da precedência — que é exatamente
por isso que ela foi extraída para uma função pura com 35 testes, em vez de ficar embutida
num componente.

Tudo abaixo vai para o **checkpoint humano (Plano 08.5-17, Windows nativo, 2 máquinas)**:

1. **A REGRESSÃO Nº 1 — ensurdecer continua ensurdecendo.** Com alguém falando, clicar em
   ensurdecer: o som some **de todo mundo**, na hora. Desensurdecer: volta. É comportamento
   verificado da Fase 7 e este plano mexeu em quem o aplica.
2. **Ensurdecer GANHA do volume individual.** Ajustar o fulano para 30%, ensurdecer (silêncio
   total), desensurdecer — e o fulano tem que voltar **em 30%**, não em 100%. É a briga que
   motivou o plano inteiro.
3. **O ajuste NÃO volta sozinho quando alguém entra na call.** Ajustar A para 20%, pedir para
   B **entrar** no canal, e conferir que A continua em 20%. Era o sintoma clássico da
   arquitetura antiga.
4. **Quem entra DEPOIS já entra com o meu ajuste.** Silenciar A para mim, A sai do canal e
   volta: A tem que voltar **silenciado**, sem eu tocar em nada.
5. **Silenciar UM não silencia os outros.** Com A e B falando ao mesmo tempo, silenciar A: B
   continua audível no volume normal. Este é o item que precisa de três pessoas.
6. **Silenciar para mim NÃO muta a pessoa para os outros.** Confirmar na máquina de C que A
   continua sendo ouvido normalmente — e que o ícone de mute de A **não** mudou para ninguém.
7. **O ajuste sobrevive ao reinício do app.** Ajustar, fechar o app inteiro, reabrir, entrar
   no mesmo canal: o volume tem que estar como foi deixado. E, se houver uma segunda máquina
   com a mesma conta: lá o volume tem que estar **normal** (é preferência de máquina, não de
   conta).
8. **O slider funciona por teclado dentro do menu do Radix.** Tab/Enter para abrir, chegar ao
   slider, setas esquerda/direita mudando o valor. **É esta observação que decide o desvio 3**
   — se funcionar, os itens "Aumentar/Diminuir volume" saem; se não funcionar, o slider sai.
9. **O menu abre pelos três caminhos** no ladrilho do participante: clique, `Enter` com o
   ladrilho focado e botão direito. E o anel de foco aparece.
10. **O menu não aparece no meu próprio ladrilho** nem na prévia de um canal de voz em que
    não estou.
11. **O estado visual de silenciado é percebido**: avatar mais apagado + ícone `VolumeX`, sem
    se confundir com o badge de mute (que é vermelho, no canto oposto). E a porcentagem ao
    lado do nome quando o volume foi baixado.
12. **200% faz falta?** Hoje o teto é 100% pelo motivo da seção (b). Se um microfone baixo
    continuar baixo demais no volume cheio, a decisão sobre `webAudioMix` deixa de ser
    teórica — e junto com ela vem retestar o **seletor de dispositivo de saída** (VOICE-20),
    que é o que essa mudança pode quebrar.
13. **Nada de volume aparece na `MemberList`** — decisão registrada, confirmar que é o
    esperado.
14. **No layout de compartilhamento (`share`) o menu não é alcançável** (desvio 2): confirmar
    se o contorno "Ocultar tela → ajustar → Mostrar tela" é aceitável ou se a extração do
    `ParticipantTile` para a faixa vira trabalho.
