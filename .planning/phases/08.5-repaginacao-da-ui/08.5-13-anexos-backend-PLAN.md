# API de storage do Convex, CONFERIDA na versão instalada (convex@1.44.0,
# node_modules/convex/dist/cjs-types/server/storage.d.ts) — não de memória:
#   - mutation: `ctx.storage.generateUploadUrl(): Promise<string>`
#     O cliente faz POST do arquivo nessa URL e recebe `{ storageId }` em JSON.
#   - query/mutation: `ctx.storage.getUrl(id: Id<'_storage'>): Promise<string | null>`
#     `null` quando o arquivo não existe mais.
#   - metadata: `ctx.db.system.get('_storage', storageId)` →
#     `{ _id, _creationTime, sha256, size, contentType? }`.
#     (`ctx.storage.getMetadata` existe mas está DEPRECADO nesta versão — usar
#     `db.system.get`.)
#   - `ctx.storage.delete(id)` para apagar.
</context>

<task type="auto">
  <name>Task 1: Campo attachments no schema e URL de upload autorizada por canal</name>
  <files>convex/schema.ts, convex/messages.ts</files>
  <action>
    **schema.ts** — em `messages`, acrescentar:
    ```ts
    attachments: v.optional(
      v.array(
        v.object({
          storageId: v.id('_storage'),
          name: v.string(),
          size: v.number(),
          contentType: v.optional(v.string())
        })
      )
    )
    ```
    Guardar `name`/`size`/`contentType` na própria mensagem, e não só o
    `storageId`: o nome original do arquivo não existe no storage do Convex
    (só sha256, tamanho e content-type), e é o nome que a UI precisa mostrar.
    `size` duplicado do `_storage` de propósito — evita um `db.system.get` por
    anexo a cada leitura do histórico paginado.
    Não criar tabela própria: um anexo não tem vida independente da mensagem,
    e uma tabela extra custaria mais uma consulta por mensagem na listagem
    paginada, que é o caminho mais quente do chat.

    **messages.ts** — nova mutation:
    ```ts
    export const generateUploadUrl = mutation({
      args: { channelId: v.id('channels') },
      handler: async (ctx, { channelId }) => {
        const { channel } = await requireChannelMembership(ctx, channelId)
        if (channel.type !== 'text') throw new Error('...')
        return ctx.storage.generateUploadUrl()
      }
    })
    ```
    O `channelId` existe SÓ para autorizar: sem ele, qualquer usuário
    autenticado poderia obter URL de upload e gravar arquivo no storage do
    projeto sem ser membro de nada. É o mesmo princípio de SRV-06 (não-membro
    não aprende nem escreve nada), aplicado ao storage.

    Definir e exportar os limites como constantes no topo do arquivo, com
    comentário justificando:
    ```ts
    export const MAX_ATTACHMENT_BYTES = 25 * 1024 * 1024 // 25 MB por arquivo
    export const MAX_ATTACHMENTS_PER_MESSAGE = 5
    ```
    25 MB é o mesmo teto que o grupo já conhece do Discord gratuito, e é grande
    o bastante para print, log e clipe curto. O custo real a registrar: o plano
    gratuito do Convex tem cota finita de file storage — 20 pessoas mandando
    vídeo de 25 MB consomem isso rápido. Não construir cota nem expurgo
    automático nesta fase (seria feature nova, não anexo); registrar como risco
    conhecido no SUMMARY.
  </action>
  <verify>`npx tsc --noEmit -p tsconfig.convex.json` limpo; `grep -n "generateUploadUrl" convex/messages.ts` retorna a mutation com `requireChannelMembership` antes do `return`.</verify>
  <done>O schema aceita anexos opcionais e só membro do canal obtém URL de upload.</done>
</task>

<task type="auto">
  <name>Task 2: sendMessage aceita anexos e listMessages devolve URL por anexo</name>
  <files>convex/messages.ts</files>
  <action>
    **sendMessage** — acrescentar arg opcional:
    ```ts
    args: {
      channelId: v.id('channels'),
      content: v.string(),
      attachments: v.optional(v.array(v.object({ storageId: v.id('_storage'), name: v.string() })))
    }
    ```
    O cliente manda só `storageId` + `name`; `size` e `contentType` o SERVIDOR
    lê de `ctx.db.system.get('_storage', storageId)` e grava junto — cliente
    não é fonte da verdade sobre tamanho de arquivo (senão o limite é
    contornável mandando `size: 1`).

    Validações, na ordem:
    1. `requireChannelMembership` e canal do tipo texto (já existe).
    2. `attachments.length <= MAX_ATTACHMENTS_PER_MESSAGE`, senão erro legível.
    3. Para cada anexo: `db.system.get('_storage', storageId)`. Se `null` →
       erro ("Arquivo não encontrado"), porque `storageId` inventado não pode
       virar linha no banco. Se `size > MAX_ATTACHMENT_BYTES` → erro com o
       limite em MB na mensagem. **Esta é a checagem que vale**: o cliente
       também vai checar antes de subir (Plano 08.5-14), mas quem decide é o
       servidor.
    4. Conteúdo: hoje a regra é 1..2000 caracteres. Passa a ser: se há pelo
       menos um anexo, `content` pode ser vazio (mensagem só com imagem é o
       caso normal); sem anexo, a regra atual continua. O teto de 2000
       caracteres não muda.
    5. Gravar `attachments` no insert só quando houver algum (não gravar
       `attachments: []`, para o documento continuar idêntico ao de antes
       quando não há anexo).
    Ordem importa: validar antes de inserir, e nunca inserir mensagem
    parcialmente válida.

    **listMessages** — no `Promise.all` que já enriquece cada mensagem com o
    autor, acrescentar o enriquecimento dos anexos:
    ```ts
    attachments: await Promise.all(
      (message.attachments ?? []).map(async (a) => ({
        ...a,
        url: await ctx.storage.getUrl(a.storageId)  // null se o arquivo sumiu
      }))
    )
    ```
    `url: null` NÃO é erro: é o caso "arquivo apagado/expirado", e a UI
    (Plano 08.5-14) mostra "arquivo indisponível" em vez de uma imagem
    quebrada. Documentar isso no comentário — é a pergunta que o CONTEXT.md
    levantou ("o que acontece quando o arquivo some") e a resposta fica no
    código, não na cabeça de alguém.

    Custo a registrar no SUMMARY: `getUrl` por anexo, por mensagem, a cada
    página do histórico. Como a maioria das mensagens não tem anexo, o
    `?? []` faz o custo ser zero no caminho comum.
  </action>
  <verify>`npx tsc --noEmit -p tsconfig.convex.json` limpo; `grep -n "storage.getUrl" convex/messages.ts` retorna o enriquecimento; `grep -n "MAX_ATTACHMENT_BYTES" convex/messages.ts` retorna a checagem dentro do sendMessage.</verify>
  <done>Enviar mensagem com anexo grava metadados verificados pelo servidor, e listar mensagens devolve URL utilizável ou `null`.</done>
</task>
