## (a) A mudança de semântica do clique no canal de voz — REGISTRO OBRIGATÓRIO

**Clicar num canal de voz em que você JÁ ESTÁ não desconecta mais. Volta ao palco.**

`handleVoiceChannelClick` (`ChannelSidebar.tsx`) foi reescrita inteira, não emendada:

```tsx
function handleVoiceChannelClick(channel: Doc<'channels'>): void {
  if (joinedVoiceChannelId === channel._id) {
    showStage()
    return
  }
  setSelectedChannelId(channel._id)
  setJoinedVoiceChannelId(channel._id)
}
```

O `setSelectedChannelId` **incondicional** que existia (commit `0265537`) tinha que sair:
pela regra 3 das transições do provider, selecionar um canal desliga o palco — então
reclicar no canal conectado desligaria exatamente o palco que o clique veio ligar. O
oposto do pretendido.

**Desconectar é agora exclusividade do botão de telefone do rodapé** (`VoiceControlBar`,
`PhoneOff`, "Sair do canal de voz"). Nenhum outro caminho sai da call.
`grep -n "setJoinedVoiceChannelId(null)" src/renderer/src/components/shell/ChannelSidebar.tsx`
não retorna nada.

**Item explícito para o roteiro do checkpoint humano (Plano 08.5-17):** clicar no canal de
voz conectado NÃO pode desconectar — tem que voltar para o palco.

## (b) O `<video>` desmonta ao sair do palco e remonta ao voltar — REGISTRO OBRIGATÓRIO

**Isto é o comportamento esperado e é a primeira coisa que alguém vai achar que é bug.**

Ao navegar do palco para um canal de texto, `ConversationArea` deixa de renderizar
`CallStage` → o React desmonta o `ScreenShareTile` → o cleanup do efeito roda
(`entry.track.detach(element)` + `element.remove()`) e o `<video>` sai do DOM. Ao voltar
ao palco, o componente monta de novo, o efeito roda de novo e o `<video>` renasce de
`track.attach()`.

Por que isso é seguro: **`screenShareTracks` vive em `voice-context`, não no componente**.
A inscrição na track não é desfeita pela navegação — só o elemento de exibição é. Este é
literalmente o contrato do Plano 08-06: o elemento existe enquanto o componente existe, e
é o React (não o SDK) quem o remove.

O que **não** dá para afirmar daqui: que o vídeo reaparece **e não volta congelado**.
Isso é WSL2 sem tela, sem Windows e sem uma segunda máquina compartilhando. Item
obrigatório do checkpoint (§ "O que fica para o humano", abaixo).

## O modelo de estado que passou a existir

Uma função pura e um booleano. Nenhuma entidade nova.

**`src/renderer/src/lib/stage-view.ts`** — `resolveMainView(input): MainView`, genérica
sobre o tipo do id (sem React, sem Convex, sem DOM; roda no `edge-runtime` global). Regras
**nesta ordem**, e a ordem é a regra:

1. `joinedVoiceChannelId !== null && viewingStage` → `stage` do canal **conectado**. O
   palco ganha da seleção — é isto que faz "voltar para a call" funcionar com um canal de
   texto selecionado.
2. `selectedChannelType === 'text'` → `text`. **Alcançável com a call ativa** — é a call
   continuando enquanto se lê o texto, o ponto inteiro do plano.
3. `selectedChannelType === 'voice'` → `voice-preview` (ver quem está lá sem entrar).
4. Resto → `empty`.

**`viewingStage` no `SelectionContext`**, com as transições **dentro do provider** (não em
cada chamador):

| Transição | Efeito |
|---|---|
| `setJoinedVoiceChannelId(id)` com `id !== null` | `viewingStage = true` |
| `setJoinedVoiceChannelId(null)` | `viewingStage = false` |
| `setSelectedChannelId(...)` | `viewingStage = false` |
| `setSelectedServerId(...)` (**acréscimo, ver Desvios**) | `viewingStage = false` |
| `showStage()` | `viewingStage = true` |

Não persistido: é estado de sessão. Ao reabrir o app não existe call ativa, então o valor
inicial correto é sempre `false`.

Detalhe que ficou comentado no código porque é fácil de quebrar: em
`handleVoiceChannelClick`, `selectChannel` (que zera) roda **antes** de `joinVoiceChannel`
(que liga) no mesmo handler; o React agrupa os dois `setViewingStage` e vence o último.
Inverter a ordem das duas chamadas quebraria a entrada na call sem quebrar teste nenhum.

## Deviations from Plan

### 1. [Rule 2 — lacuna crítica] Trocar de SERVIDOR também desliga o palco

- **Encontrado em:** Task 2, ao escrever as três transições.
- **Problema:** o plano lista três transições e nenhuma cobre `setSelectedServerId`. Só que
  `selectServer` zera `manualChannelId` e força a reseleção do 1º canal de texto do novo
  servidor — ou seja, é navegação. Sem desligar o palco ali, quem está numa call e clica
  noutro servidor **não veria a tela mudar**: o palco continuaria na frente do canal
  recém-selecionado, e o usuário concluiria que clicar no servidor não funciona.
- **Correção:** `setViewingStage(false)` em `selectServer`, com comentário apontando para a
  mesma regra 3. Quatro linhas.
- **Por que não é mudança arquitetural:** é a regra que o plano já escreveu ("navegar para
  um canal é pedir para ver aquele canal"), aplicada ao único outro caminho de navegação
  que existe. Nenhum estado novo, nenhuma decisão de design reaberta.
- **Commit:** `197aa10`
- **Nota relacionada, sem mudança de código:** `goHome()` **não** desliga o palco de
  propósito — no modo Início o `AppShell` nem renderiza `ConversationArea` (renderiza
  `FriendsPanel`), então voltar ao servidor com o palco ligado é o comportamento desejável
  (você estava na call).

### 2. [Rule 1 — a convenção da fase brigaria com o contrato da F8] `ScrollArea` não substituiu o `overflow-y-auto`

- **Encontrado em:** Task 3. O próprio plano previa este caso e mandava decidir.
- **Causa:** `ScreenShareStage` se dimensiona com `flex-1 min-h-40`, contando com um pai
  flex de altura definida. O `Viewport` do Radix (ver `components/ui/scroll-area.tsx`)
  embrulha os filhos num elemento `display: table` — o pai deixa de ser flex, `flex-1` vira
  letra morta e a região de vídeo ficaria com os 160px do `min-h-40`.
- **Decisão:** manter o `overflow-y-auto` do antigo `VoiceChannelView`, com um comentário
  de 7 linhas explicando por quê. Regressão de vídeo é pior que um `overflow-y-auto`
  sobrevivente, e o layout definitivo do palco é o Plano 08.5-07 mesmo.
- **Ressalva honesta:** o `display: table` do Viewport é comportamento documentado do Radix
  e coerente com o código do wrapper, mas **não foi medido aqui** — jsdom não faz layout e
  não há tela. Se o 08.5-07 quiser tentar `ScrollArea` de novo, que meça em Windows.

### 3. [Consequência do roteamento prescrito, registrada] A prévia de canal de voz perdeu o convite "Entre no canal para ver a tela compartilhada"

- **O que mudou:** antes, um canal de voz **não** conectado renderizava
  `VoiceParticipantGrid` **+** `ScreenShareStage`, e este último mostrava a moldura
  tracejada com "Entre no canal para ver a tela compartilhada". O plano especifica que
  `voice-preview` renderiza "o grid de participantes", e é o que foi feito.
- **Impacto:** a prévia ficou só com o grid. Nenhum vídeo foi perdido (não havia vídeo
  nesse caminho — `ScreenShareStage` já devolvia `[]` quando `isConnectedHere` era falso).
- **Se o convite fizer falta**, restaurá-lo é uma linha, e o dono da região é o Plano
  08.5-07. Registrado aqui para não virar "descoberta" no checkpoint.
