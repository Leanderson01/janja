## O que mudou, arquivo a arquivo

### `MessageList.tsx` — o divisor de não lidas

As três ocorrências de `bg-red-500` / `text-red-500` viraram `bg-highlight` /
`text-highlight`. O comentário acima do componente agora registra **por que** não é
`--destructive` (vermelho aqui significa erro, mute, desconectar, conexão perdida — nada
disso é "tem mensagem nova") e marca `data-unread-divider="true"` como gancho da lógica de
scroll do CHAT-14, para ninguém remover achando que é enfeite.

`role="separator"`, `aria-label="Novas mensagens"` e `data-unread-divider="true"` saem
intactos do diff. O resto do arquivo (300 linhas) foi conferido por grep: **não havia**
nenhuma outra cor direta nem `space-*`.

Efeito colateral bom: o badge de não lidas da sidebar (Plano 08.5-08) usa o mesmo
`--highlight`, então os dois marcadores do mesmo conceito vão combinar sem ninguém
precisar combinar nada.

**Cor:**

**Feedback — o que virou toast e o que ficou inline.** Esta é a seção que o plano pediu

| Ação | Antes | Depois | Mensagem |
|---|---|---|---|
| `sendFriendRequest` OK | parágrafo `text-green-600` | `toast.success` | `Pedido de amizade enviado para {user}#{tag}` (mesma string de antes) |
| `sendFriendRequest` erro | parágrafo `text-destructive` (`sendError`) | `toast.error` | "Não foi possível enviar o pedido" + erro cru na `description` |
| `acceptFriendRequest` OK | **nada** | `toast.success` | `Agora você e {user}#{tag} são amigos` |
| `acceptFriendRequest` erro | parágrafo por linha (`rowErrors`) | `toast.error` | "Não foi possível aceitar o pedido" + `description` |
| `rejectFriendRequest` OK | **nada** | `toast.success` | `Pedido de {user}#{tag} recusado` |
| `rejectFriendRequest` erro | parágrafo por linha | `toast.error` | "Não foi possível recusar o pedido" + `description` |
| `removeFriendship` OK | **nada** | `toast.success` | `{user}#{tag} removido dos seus amigos` |
| `removeFriendship` erro | **só `console.error`** | `toast.error` | "Não foi possível remover o amigo" + `description` |
| `getOrCreateDmChannel` erro | parágrafo por linha | `toast.error` | "Não foi possível abrir a conversa" + `description` |
| **Formato de `USER#123` inválido** | parágrafo `text-destructive` | **continua inline** | `Formato inválido — use usuario#0001` |

O critério aplicado é o do plano, e está escrito em comentário no código para não se perder:
**resultado de operação de rede → toast; erro de validação do que o usuário acabou de
digitar → inline**, porque num toast ele sumiria enquanto o valor inválido continua na
tela.

Três coisas que a troca resolveu de quebra:

- **`removeFriendship` falhando era invisível** — ia só para o `console.error`. Um segundo
  cliente já tendo desfeito a amizade produzia zero feedback na tela. Agora é toast de erro.
- **Aceitar/recusar não tinham confirmação nenhuma**, só o sumiço da linha.
- **O parágrafo de erro por linha morava dentro de uma linha que a própria mutation podia
  remover da lista.** O toast não depende de a linha continuar existindo, e ainda ganha
  `aria-live` de graça (Sonner), que o parágrafo não tinha.

Os estados `rowErrors` (nas duas abas), `confirmation` e `sendError` foram removidos junto
com a UI que serviam — daí o arquivo encolher. `FriendRow` e `RequestRow` perderam a prop
`error` e o wrapper `flex-col` que existia só para pendurar o parágrafo abaixo da linha.

**Outros itens da passada de convenção:** `cn()` na classe condicional de presença e no
grupo esmaecido (`opacity-60`); nenhum `space-*` no arquivo; os **3** `<Avatar>` continuam
com os **3** `<AvatarFallback>` (não regrediu). O `import type { Id }` ficou órfão com a
saída do `rowErrors` e foi removido (era erro de typecheck, ver desvios).

### `ScreenSharePicker.tsx` — `ScrollArea`

`<div className="max-h-[60vh] overflow-y-auto pr-1">` saiu. Entrou:

```tsx
<div className="flex max-h-[60vh] flex-col">
  <ScrollArea className="min-h-0 flex-1 pr-1">
```

**Por que não o `<ScrollArea className="max-h-[60vh]">` literal do plano** (o próprio plano
previu que isso podia não rolar, e previu certo): o viewport do Radix é `size-full`, ou
seja `height: 100%`, e 100% de um pai de **altura automática** resolve para `auto`. Com
`max-h` direto no `ScrollArea`, o viewport cresceria com o conteúdo, nunca rolaria, e —
como nem o root do `ScrollArea` (`cn("relative", …)`) nem o `DialogContent` têm
`overflow: hidden` — a lista vazaria para fora do diálogo. É exatamente o sintoma que o
plano descreveu.

O plano autorizava cair para `h-[60vh]`; preferi `max-h` no wrapper flex + `min-h-0 flex-1`
no `ScrollArea` porque dá altura definida ao viewport **sem** forçar o diálogo a ter sempre
60vh quando há duas fontes só. É o mesmo idioma `flex-1 min-h-0` que o `MessageList` e o
RESEARCH da F3 já usam neste projeto. O `pr-1` foi para o `ScrollArea`: a barra do Radix é
absoluta na borda do root, então o padding vira o respiro entre ela e os cards. O racional
está em comentário no arquivo.

```
(vazio)
```

O grid continua `grid-cols-2 sm:grid-cols-3` e o `DialogFooter` continua **fora** da área

## Decisions Made

- **`--highlight` no divisor, não `--destructive`.** Vermelho neste app é erro e ação
  destrutiva. Mensagem não lida não é nenhum dos dois, e a regra travada da fase lista
  "marcador de não-lido" como um dos três usos autorizados do destaque.
- **`getOrCreateDmChannel` também virou toast**, apesar de não ser uma das quatro mutations
  de amizade que o plano nomeia. É operação de rede e o erro não se ancora a nenhum campo —
  o critério do próprio plano manda toast. Manter só ele inline obrigaria a preservar toda
  a máquina de `rowErrors` para um caso, com dois padrões de feedback convivendo no mesmo
  painel.
- **Toast de erro com título curto + erro cru na `description`.** A UI antiga jogava a
  mensagem crua do Convex (com request id e prefixo `[CONVEX M(...)]`) na tela como texto
  principal. Como título de toast isso ficaria ilegível; como descrição, o texto continua
  disponível para depurar sem virar a manchete.
- **`DmSidebar` e `DmMessageList` não foram editados.** Estavam conformes; editar por
  editar só geraria diff para outro agente resolver.
- **Nenhum teste novo.** A onda proíbe criar arquivos fora de `files_modified`, e nenhum
  dos 5 arquivos tem teste hoje. Ver "Next Phase Readiness" para o follow-up recomendado.

## Deviations from Plan

### 1. [Rule 3 — bloqueio de typecheck] `import type { Id }` órfão no `FriendsPanel.tsx`

- **Encontrado em:** Task 2, no primeiro `npm run typecheck`.
- **Erro literal:** `FriendsPanel.tsx(17,1): error TS6133: 'Id' is declared but its value is never read.`
- **Causa:** o tipo `Id<'users'>` / `Id<'friendRequests'>` só era usado pelas assinaturas
  do `rowErrors` e dos handlers que recebiam ids soltos. Com os handlers passando a receber
  o objeto (`Friend` / `IncomingRequest`, que já carregam o id), o import ficou sem uso.
- **Correção:** import removido. Nenhum comportamento afetado.

### 2. [Rule 1 — instrução do plano produziria layout quebrado] `ScrollArea` precisou de wrapper flex

- **Encontrado em:** Task 3, ao analisar o `scroll-area.tsx` e o `dialog.tsx` do repo antes
  de escrever a mudança.
- **Problema:** `<ScrollArea className="max-h-[60vh]">`, literalmente como a ação da tarefa
  pede, **não rola**: viewport `size-full` dentro de pai com altura automática resolve
  `height: 100%` para `auto`. O próprio plano previu o sintoma e autorizou a alternativa.
- **Correção:** wrapper `flex max-h-[60vh] flex-col` + `min-h-0 flex-1` no `ScrollArea`, em
  vez do `h-[60vh]` fixo sugerido como plano B — mesma garantia de altura definida, sem
  obrigar o diálogo a ocupar 60vh quando há poucas fontes.
- **Ressalva honesta:** isto é raciocínio de CSS, não observação. jsdom não faz layout e
  WSL2 não tem tela. Ver a seção seguinte.

### 3. [Rule 2 — lacuna crítica] falha de `removeFriendship` não tinha nenhum feedback

- **Encontrado em:** Task 2, ao mapear as mutations.
- **Problema:** o `catch` só chamava `console.error`. Para o usuário, remover um amigo e
  falhar era indistinguível de não ter clicado.
- **Correção:** virou `toast.error('Não foi possível remover o amigo', { description })`.
  O comentário original sobre nunca deixar Promise rejeitada sem tratamento foi preservado.
