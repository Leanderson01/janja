<task type="auto">
  <name>Task 2: Composer com seleção e upload de arquivos</name>
  <files>src/renderer/src/components/shell/MessageInput.tsx, src/renderer/src/components/shell/ConversationArea.tsx</files>
  <action>
    **MessageInput.tsx** — acrescentar, sem quebrar o contrato atual
    (`onSend(content)` continua existindo para quem não passa anexo, que é o
    caso do DM):
    - Nova prop opcional `onSendWithAttachments?: (content: string, files: File[]) => Promise<void>`.
      Quando ausente (DM), o botão de anexo não é renderizado. Isso é o que
      permite este plano não tocar em `DmConversationView.tsx`.
    - Botão de clipe (`Paperclip` do lucide, `Button variant="ghost" size="icon"`,
      com `Tooltip` e `aria-label="Anexar arquivo"`) que dispara um
      `<input type="file" multiple hidden ref={...}>`.
    - Estado `selected: File[]`. Ao escolher, passar por `validateFiles`:
      aceitos entram na lista; recusados viram `toast.error` com nome e motivo
      ("arquivo.zip: acima de 25 MB"). Validar ANTES de subir — descobrir o
      limite depois de esperar o upload é a pior versão desse erro.
    - Lista dos escolhidos acima do textarea: nome truncado + tamanho
      (`formatBytes`) + botão "remover" com `aria-label` próprio por arquivo.
    - `Enter` com anexos selecionados e texto vazio deve ENVIAR (mensagem só
      com imagem é o caso normal). Não mexer na guarda de IME nem no
      Shift+Enter (Plano 08.5-10) — só na condição de "vazio".
    - Durante o envio: `disabled` no textarea, no botão de anexo e no de
      enviar, com rótulo "Enviando…". **Sem barra de progresso**: `fetch` não
      expõe progresso de upload sem trocar por `XMLHttpRequest`, e trocar o
      transporte por causa de uma barra é custo alto para ganho pequeno num
      grupo de 10 pessoas em arquivos de até 25 MB. Registrar a escolha.
    - **Falha não limpa a seleção.** Se o envio rejeitar, os arquivos
      escolhidos continuam na lista e os controles voltam a ficar ativos, para
      o usuário tentar de novo. Só limpar em caso de sucesso.

    **ConversationArea.tsx** — em `TextChannelView`, implementar
    `handleSendWithAttachments(content, files)`:
    1. `const uploadUrl = await generateUploadUrl({ channelId })`
       (`useMutation(api.messages.generateUploadUrl)`).
       Uma URL por arquivo — `generateUploadUrl` devolve URL de uso único.
    2. Para cada arquivo: `fetch(uploadUrl, { method: 'POST', headers: { 'Content-Type': file.type }, body: file })`
       → `const { storageId } = await res.json()`. Se `res.ok` for falso,
       lançar com mensagem legível.
    3. `sendMessage({ channelId, content, attachments: [{ storageId, name: file.name }, ...] })`.
    4. Qualquer falha → `toast.error(...)` e re-lançar/rejeitar, para o
       composer saber que não deve limpar a seleção.
    Subir em série (um `for...of` com `await`), não em paralelo: 5 uploads de
    25 MB simultâneos no upload doméstico brasileiro é a receita para todos
    falharem juntos — e é o mesmo raciocínio que já governa o preset "fluida"
    do compartilhamento de tela.
    Caso de borda a tratar: arquivo subiu mas `sendMessage` falhou → o arquivo
    fica órfão no storage. Não construir coleta de lixo agora (seria feature
    nova); registrar como risco conhecido no SUMMARY.
  </action>
  <verify>`npm run typecheck` limpo; `npm run build` passa; `grep -n "onSendWithAttachments" src/renderer/src/components/shell/MessageInput.tsx src/renderer/src/components/shell/ConversationArea.tsx` mostra a prop nos dois lados; `npx vitest run src/renderer/src/components/shell/MessageInput.test.tsx` continua passando (o teste do Plano 03 não pode ter sido quebrado).</verify>
