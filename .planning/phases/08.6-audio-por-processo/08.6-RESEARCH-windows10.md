# Fase 8.6 — Windows 10: o portão de versão está errado

**Pesquisado:** 2026-08-25
**Domínio:** WASAPI process loopback (`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`) em Windows 10
**Pergunta:** o corte em build 20348 exclui o Windows 10 do Leo. Ele está certo?
**Confiança geral:** HIGH na resposta da pergunta 1. MEDIUM nas ressalvas. LOW em tudo da pergunta 2 que não seja "não faça".
**Ambiente:** WSL2, sem Windows. **Nada aqui foi executado.** Ver §7 para o que o Leo precisa rodar.

---

## 0. A resposta, em uma frase

**O portão está errado. `MIN_WINDOWS_BUILD_FOR_PROCESS_LOOPBACK = 20348` deve virar `19041`**, e com isso o
Windows 10 2004+ — inclusive o 22H2 (19045) do Leo — passa a poder capturar áudio por processo.
A documentação da Microsoft diz 20348; **o OBS Studio, que roda esse mesmo caminho de código em
milhões de máquinas desde agosto de 2022, tem no fonte um portão em 19041 com o comentário
literal `/* MS says 20348, but process filtering seems to work earlier */`** — e há usuários de
Windows 10 22H2 build 19045 abrindo *bugs de comportamento fino* do recurso, o que só é possível
se o recurso funciona neles.

**O custo da correção é trocar um número.** Não é uma fase, não é um plano, é uma constante,
dois textos de tela e três testes que citam o número velho.

> **Confiança: HIGH.** O número oficial é 20348, ele continua lá em 2026, e ele é maior que
> qualquer Windows 10 de consumidor (o 22H2 é 19045). A pesquisa anterior leu isso corretamente.

O que muda a interpretação: **20348 é o build do Windows Server 2022**, e era o build de
Insider mais recente quando a página foi escrita (janeiro de 2021, antes de o Windows 11
existir publicamente). Esse campo de metadado (`req.target-min-winverclnt`) descreve **em qual
SDK/build a API foi documentada**, não necessariamente **a partir de qual build o binário do
sistema aceita a chamada**. Não é o único caso — mas isso, sozinho, seria opinião. O que
resolve é o campo.

### 1.2 O que o código C++ do pacote realmente exige

Li de novo, agora com esta pergunta, o fonte que veio dentro do `.tgz`
(`node_modules/loopback-capture/src/*`, o pacote já instalado):

```

(nenhum resultado)
```

**O pacote não tem nenhuma checagem de versão de Windows — nem em compilação, nem em runtime.**
A única coisa parecida está no JavaScript (`dist/index.cjs`) e é um `console.warn` sobre
plataforma/arquitetura, não sobre build:

```js

  console.warn(`This package is currently only available for Windows 10 x64 and later`)
```

Ou seja: **o "Windows 10 x64 e superior" do README é marketing, não um contrato verificado**.
Mas o próprio README, na seção "Why and how?", é mais preciso e concorda com a tese:

> "**Per-process capture** uses `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` (**Windows 10 2004+**),
> activated asynchronously via `ActivateAudioInterfaceAsync`"

Windows 10 2004 = build **19041**.

**O achado estrutural que importa mais que o README** (`src/LoopbackCapture.cpp:83-105`): a
ativação é assíncrona no Windows, mas o pacote a torna **síncrona para quem chama**:

```cpp
wil::com_ptr_nothrow<IActivateAudioInterfaceAsyncOperation> asyncOp;
RETURN_IF_FAILED(ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK,
                 __uuidof(IAudioClient), &activateParams, this, &asyncOp));

// Wait for activation completion
m_hActivateCompleted.wait();

return m_activateResult;
```

E `m_activateResult` sobe até `LoopbackCaptureWrap::Start()`, que lança para o JS
(`src/LoopbackCaptureWrap.cpp:84-92`):

```cpp
HRESULT hr = m_capture->StartCaptureAsync(processId, includeProcessTree, tsfn);
if (FAILED(hr))
{
   m_capture.Reset();
   Napi::Error::New(env, "Failed to start loopback capture (HRESULT " + HResultToString(hr) + ")")
       .ThrowAsJavaScriptException();
```

**Consequência: `capture.start(pid, false, cb)` devolve o HRESULT da ativação do Windows, de
forma síncrona, na mesma chamada.** O "teste de tempo de execução" que a pergunta 1 pede não
precisa ser construído — ele já existe, já está ligado no `screenshare-audio.ts` (`start-failed`
com `detail` carregando o HRESULT), e é ele que o portão de versão está impedindo de rodar.

> Confiança: **HIGH** (li o fonte publicado, não o GitHub).

### 1.4 A zona cinzenta REAL — e ela não é o número do build

A zona cinzenta existe, mas não está onde o portão a colocou. Todas as fontes de campo
convergem para: **o build precisa ser ≥ 19041 E a máquina precisa estar atualizada.** README do
`win-capture-audio`, seção Troubleshooting:

> "**Application Audio Output Capture source not picking up any audio:** this happens when your
> Windows is too old and does not have support for the API. **Note that even if you have a more
> recent major version such as `20H2` you will still need the latest updates for the plugin to
> work.** If you are on a very old version you might need more than one update for this to work,
> and the second update might not show up for a few days after the first update."

Três consequências que o plano precisa absorver:

1. **O modo de falha em Windows 10 pouco atualizado é SILÊNCIO, não HRESULT.** "not picking up
   any audio" — não "erro ao ativar". O `start()` pode não lançar e mesmo assim nunca chegar
   chunk. Isso é exatamente o terceiro modo de falha que a pesquisa original previu e que o
   **watchdog de 15s já cobre**. Confiança: MEDIUM (é a frase de um autor de plugin, não uma
   afirmação da Microsoft).
2. **`os.release()` NÃO enxerga a revisão (UBR).** Ele devolve `"10.0.19045"`, sem o `.2846`.
   Ou seja: **é impossível, pelo número, distinguir um 19045 atualizado de um 19045 de 2022.**
   Isso derruba de vez a ideia de que o portão de versão pode ser a barreira que decide — ele
   não tem a informação que decide. (Se algum dia for necessário, o UBR está em
   `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\UBR`; não vale o custo.)
3. **Bom: o Windows 10 de hoje é o mais atualizado que ele jamais será.** 19041/19042/19043/
   19044/19045 são o mesmo ramo de serviço (Vibranium) — diferem por pacote de habilitação,
   não por binários de áudio. O Windows 10 22H2 saiu de suporte em 2025-10-14, então a máquina
   do Leo tem, na pior das hipóteses, o cumulativo de outubro de 2025 — **quatro anos** depois
   do KB que fez o recurso funcionar. O risco de "atualizado de menos" é baixo nesta máquina em
   específico, e alto só para quem congelou o Windows em 2020/2021.

### 1.5 A ressalva honesta que sobra: modo EXCLUIR em Windows 10

Toda a evidência de campo acima é de **modo INCLUIR**. O OBS usa
`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` fixo no código
(`plugins/win-wasapi/win-wasapi.cpp:698-699`); o `win-capture-audio` idem. **Não achei nenhum
relato de campo de `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` em Windows 10.**

O que dá para dizer com honestidade:

- É **o mesmo campo, da mesma struct, no mesmo blob, na mesma chamada de ativação**. Não é uma
  segunda API com um segundo gate de versão: é um enum de dois valores dentro do
  `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS`. Ou o Windows entende o blob, ou não entende.
- Portanto o Windows 10 **não introduz um risco novo** para o modo EXCLUIR: ele já era MEDIUM na
  pesquisa original (§3.2: *"MEDIUM de que ela FUNCIONA como esperado — o modo excluir é muito
  menos rodado no mundo real"*). A pergunta "EXCLUIR funciona?" é a mesma no Windows 11 e no
  Windows 10, e ela só se responde na máquina.
- **Confiança: MEDIUM.** Se EXCLUIR falhar, ele vai falhar no Windows 11 do mesmo jeito, e a
  fase inteira cai — não é um problema de Windows 10.

### 1.6 Veredito, com todas as letras

> **O portão está errado. O Windows 10 22H2 (build 19045), atualizado, tem o process loopback,
> e o `loopback-capture` pode usá-lo. O corte correto é 19041 — o mesmo do OBS Studio — e a
> barreira que realmente decide é tentar `start()` e ler o HRESULT, mais o watchdog de silêncio
> que já existe.**
>
> A correção é trocar `20348` por `19041` em `screenshare-audio-types.ts`. Todo o resto do
> mecanismo — as três camadas do portão, o `start-failed` com HRESULT, o watchdog de 15s, a
> degradação para sem áudio — **já está construído e correto**. A fase 8.6 não errou o desenho;
> errou um número, e errou por confiar na documentação da Microsoft, que é a fonte que
> normalmente se deve preferir. Não é um erro que mereça culpa; é um erro que merece uma linha
> de diff e um comentário citando o OBS.

**Por que 19041 e não apagar o portão de versão inteiro?** O argumento de apagar é bom: o
HRESULT é mais honesto que um número, e o número não vê a revisão (§1.4.2). O argumento de
manter é mais barato: abaixo de 19041 a API **comprovadamente não existe** (Windows 10 1909 e
anteriores, Windows 8, Windows 7), e nesses casos a alternativa é carregar um `.node`, ativar
um dispositivo virtual inexistente e possivelmente esperar 15 segundos de watchdog para
descobrir. Um `if` que custa uma comparação de inteiros e evita isso é defesa em profundidade
barata — desde que fique escrito no código que **ele nunca é a barreira que decide**, o que o
comentário atual em `screenshare-audio-types.ts` já diz muito bem. **Mantenha o portão, corrija
o número.**

## 2. Pergunta 2 — se o portão estivesse certo (avaliação, para registro)

Escrevo isto porque foi pedido e porque o critério de decisão importa se o teste da §7 falhar.
**Nenhum destes caminhos deveria ser construído antes de o Leo rodar o teste da §7.**

### 2.1 Caminho 1 — loopback de dispositivo como escolha explícita e informada

**O que é:** naquela máquina, oferecer o caminho velho (`audio: 'loopback'` do Electron) com um
texto que não esconde nada: *"teu Windows não separa áudio por aplicativo; dá para mandar o som,
mas as outras pessoas vão se ouvir de volta."*

**Custo:** baixíssimo. O código já existiu; é uma condição no `screenshare.ts` e um ramo de UI.

**O que quebra:** o defeito de 2026-08-20 volta, agora por consentimento. E o consentimento é
falso em um ponto que importa: **quem paga o preço não é quem escolhe.** Quem liga o toggle é o
único participante que **não** vai se ouvir. As outras 3 pessoas recebem sua própria voz com
~300–500 ms de atraso — o efeito de *delayed auditory feedback*, que não é "chato", é
incapacitante: torna quase impossível falar. O AEC do WebRTC delas **não cobre isso**: o AEC
cancela o que sai do alto-falante local em relação ao microfone local; a voz que volta pelo
screenshare chega como **outra track remota**, indistinguível de um terceiro falando.

**Sobrevive ao critério "melhor sem som do que todo mundo se ouvindo"?**
**Não como está.** Sobreviveria numa forma mais estreita, e só nela: **permitido apenas quando o
compartilhador está sozinho na call, ou quando todos os outros estão mudos** — que é o caso real
de "quero mostrar um vídeo para uma pessoa que só vai assistir". Isso é verificável em runtime
(`room.remoteParticipants` + estado de mute) e transformaria a proibição em
*"proibido quando há outra fonte de voz ativa"*, que é uma regra defensável, não uma renúncia.

**Recomendação sobre a proibição da Fase 8.6:** **mantenha-a como está** (`startSystemAudio` e
`audio: 'loopback'` nunca concedidos). Ela custa nada enquanto o caminho por processo funcionar,
e o momento de reabrir a discussão é *depois* de o teste da §7 falhar — não antes. Uma proibição
que se afrouxa por hipótese não era uma proibição.

> Confiança: HIGH no diagnóstico do eco (é o defeito observado em 2026-08-20 com 4 pessoas).
> MEDIUM na afirmação sobre o AEC das outras pontas (raciocínio arquitetural sobre o AEC3 do
> WebRTC, não medição).

### 2.2 Caminho 2 — cancelamento de eco por software (NLMS num AudioWorklet)

**Seja cético, foi pedido. Sou.**

O caso é, no papel, o mais fácil que existe para um cancelador: o sinal de referência é
**digital**, não passou por alto-falante nem por sala, está na mesma taxa (48 kHz) e no mesmo
relógio de dispositivo do sinal capturado. Não é pesquisa de doutorado: NLMS é um algoritmo de
livro-texto, e existem implementações de FDAF/NLMS em WASM.

O que mata na prática, em ordem de gravidade:

1. **O `loopback-capture` DESCARTA buffers silenciosos** (`LoopbackCapture.cpp:514`,
   `IsBufferSilent(..., -70)`). Um cancelador adaptativo precisa de **fluxo contínuo e
   alinhamento temporal amostra a amostra**. Um fluxo com buracos de duração desconhecida
   destrói o alinhamento a cada trecho quieto e força o filtro a reconvergir. Isso não é um
   detalhe de ajuste: é incompatibilidade de contrato. Precisaria de fork do pacote.
2. **O projeto usa `webAudioMix: false`.** Verificado: `voice-context.tsx:348` é
   `new Room()` sem opções, e o default do `livekit-client` 2.22 é `webAudioMix: false` — o SDK
   toca cada participante num `<audio>` e **não existe AudioContext com a mistura remota**. Ter
   a referência exige `webAudioMix: true`, que muda o caminho de reprodução da call inteira,
   o `setVolume` por participante (`participant-volumes.ts` documenta isso em detalhe) e o
   `switchActiveDevice('audiooutput')`. **É uma mudança arquitetural na parte do app que menos
   pode quebrar** — a call — para consertar a parte que menos importa — o áudio do
   compartilhamento.
3. **O atraso é desconhecido, variável e grande.** Entre "escrevemos a amostra no AudioContext"
   e "ela reaparece no loopback" há: buffer do WebAudio, mixer do Windows, APOs do driver,
   Spatial Sound se ligado, o buffer do WASAPI. Antes de o NLMS rodar é preciso **estimar esse
   atraso** (correlação cruzada, recalculada quando ele mudar). Isso é a parte que os
   canceladores de verdade acertam com anos de ajuste.
4. **O critério do projeto é implacável com a solução parcial.** Um NLMS que suprime 15 dB não
   entrega "melhor"; entrega "todo mundo se ouvindo mais baixinho" — que é exatamente o que o
   critério recusa. Para a voz sumir de verdade seriam ~40 dB, com música e jogo tocando por
   cima (double-talk permanente), num filtro que precisa ficar convergido durante toda a
   transmissão.
5. **Nada disto é testável neste ambiente.** Zero.

**Veredito: NÃO.** Não é doutorado, mas é semanas de trabalho de DSP, um fork do pacote nativo,
uma mudança arquitetural na reprodução da call, e o desfecho mais provável é "quase funciona",
que é o pior desfecho possível para este critério. Se o Windows 10 fosse mesmo incapaz, o
Caminho 1 restrito (§2.1) entrega 80% do valor com 1% do custo.

> Confiança: HIGH nos itens 1 e 2 (li o código dos dois). MEDIUM nos itens 3 e 4 (teoria de AEC
> bem estabelecida, aplicada a um caso que não medi).

### 2.3 Caminho 3 — rotear a saída da call para outro dispositivo (`setSinkId`)

**Como funcionaria:** call sai no dispositivo B (fone), jogo sai no dispositivo A (padrão), e o
loopback clássico do Electron captura A. Sem eco, por construção, sem nenhuma API nova.

**Por que não funciona na prática — três motivos independentes, e o primeiro já basta:**

1. **O usuário precisa OUVIR as duas coisas, e passam a sair de lugares físicos diferentes.**
   Para o esquema funcionar, o jogo tem de tocar num dispositivo que **não** é o fone onde a
   call está. Ou o usuário ouve o jogo pelas caixas da sala enquanto usa fone para a call
   (bizarro, e o microfone captura as caixas), ou ele não ouve o jogo. **Não existe
   configuração de uma pessoa com um fone só em que isso feche.**
2. **O `audio: 'loopback'` do Electron não deixa escolher o dispositivo.** Ele captura o
   dispositivo de renderização **padrão**. Não há parâmetro. Então o esquema depende de o
   usuário manter o jogo no dispositivo padrão e a call fora dele — configuração manual, por
   app, no mixer de volume do Windows, que o usuário refaz a cada reinstalação.
3. **A variante que realmente fecha exige software de terceiros** (VB-Audio Cable /
   VoiceMeeter): mandar a call para um cabo virtual e monitorá-lo no fone junto com o jogo. É o
   que streamers fazem, é uma instalação de driver, e está fora do que um app de call pode
   pedir.

**E `loopbackWithMute`?** Também não. A doc do Electron
(`electron.d.ts:23719-23723`) descreve as duas strings; a `loopbackWithMute` **silencia a
reprodução local do dispositivo capturado** — ou seja, quem compartilha para de ouvir o que está
compartilhando (e a call junto, se estiverem no mesmo dispositivo). Já estava correto na
Armadilha 2 da pesquisa original.

**Veredito: NÃO**, exceto como instrução de documentação para o usuário avançado que já tem
VoiceMeeter. Não vira código.

> Confiança: HIGH nos motivos 1 e 3 (raciocínio físico + prática conhecida).
> MEDIUM no motivo 2 (a doc do Electron não menciona seleção de dispositivo; ausência de
> menção não é prova de ausência — mas não achei nenhuma API que a ofereça).

### 2.4 Caminhos que você não listou

**(a) Atualizar para o Windows 11.** Merece estar na lista por honestidade: o Windows 10 22H2
saiu de suporte em **2025-10-14**. Se a máquina do Leo é elegível, o upgrade é gratuito e
resolve *este* problema e vários outros. É a resposta certa para o usuário, e a resposta errada
para o produto (o app não pode exigir isso de quem instalar). Depois do §1, deixou de ser
necessário para o Leo.

**(b) Modo INCLUIR mirando o PID da janela compartilhada.** Não ajuda: é a **mesma** API, o
**mesmo** gate de versão, e ainda custa o HWND→PID que a pesquisa original rejeitou (§7 dela).
Só entra na conversa se o modo EXCLUIR falhar e o INCLUIR funcionar na mesma máquina — o que
seria um achado interessante, e é por isso que o teste da §7 vale a pena rodar nos dois modos.

**(c) `audio: WebFrameMain` do Electron.** Existe (`electron.d.ts:23721`: *"If a WebFrameMain is
specified, will capture audio from that frame"*), captura o áudio de um frame do próprio app.
Inútil aqui: queremos o áudio do **jogo**, que não é um frame nosso. Registro para ninguém
perder tempo achando que é uma saída.

**(d) Não fazer nada e compartilhar sem som.** É o comportamento de hoje e continua sendo o
fallback correto de todos os cenários acima. É o que o critério do projeto manda.

## 3. Recomendação — um caminho, e o critério que decidiria pelo outro

**Caminho recomendado: corrigir o portão para 19041 e deixar o HRESULT decidir.**

Concretamente, na ordem:

1. `MIN_WINDOWS_BUILD_FOR_PROCESS_LOOPBACK = 19041`, com o comentário citando o
   `plugin-main.cpp` do OBS e a data em que aquele número entrou em produção.
2. Os três testes que travam o número velho, invertidos (§1.7).
3. O texto `windows-too-old` do seletor, corrigido — ele hoje **afirma uma falsidade na tela**
   ("Ele existe a partir do Windows 11"), e é o item mais urgente da lista depois da constante.
4. Rodar o teste da §7 na máquina do Leo, **antes** de considerar a fase encerrada.

**O critério que decidiria pelo outro caminho:** se o teste da §7 devolver um HRESULT de falha
na ativação **em modo EXCLUIR e também em modo INCLUIR** num Windows 10 22H2 atualizado, então
o corte 19041 está errado *para esta máquina* e a conversa muda — mas note que ela muda para
"Windows 11 obrigatório", não para "construa um cancelador de eco". Nesse caso, a única opção
que sobrevive ao critério do projeto é o **Caminho 1 restrito** (§2.1): loopback de dispositivo
permitido **somente** quando não houver outra voz na call. E se o teste devolver "ativa mas só
chega silêncio", o suspeito nº 1 é nível de atualização do Windows, não a API — e a ação é
`Windows Update` até parar de oferecer coisas, e testar de novo.

## 4. O que continua verdadeiro da pesquisa original

Nada da Fase 8.6 é invalidado por este documento. Confirmado de novo, no pacote instalado:

- O modo EXCLUIR existe e chega ao Windows (`LoopbackCapture.cpp:89-91`).
- O formato é fixado em 48 kHz / estéreo / 16 bits (`:171-175`) e o `AUTOCONVERTPCM` está lá,
  contornando o `GetMixFormat() == E_NOTIMPL` do dispositivo virtual.
- Buffers silenciosos são descartados (`:514`) — e agora isso ganhou um segundo uso: é a razão
  pela qual o cancelamento de eco por software (§2.2) é inviável sem fork.
- `start()` lança com o HRESULT, **de forma síncrona**, porque a ativação assíncrona é esperada
  dentro do C++ (`:101`). Esta é a peça que o portão de versão estava tapando.

## 6. Perguntas em aberto

1. **Modo EXCLUIR em Windows 10 — nenhum relato de campo.** O que se sabe: é o mesmo campo da
   mesma struct. O que não se sabe: se o motor de áudio do Windows 10 implementa os dois valores
   do enum. **Só o teste da §7 responde**, e ele responde em 30 segundos.
2. **Qual KB exatamente habilitou o recurso no ramo 19041.** Não achei. Importa pouco: o
   Windows 10 22H2 de 2026 está muito além de qualquer candidato.
3. **`os.release()` usa `RtlGetVersion` (não mente por manifesto)?** É o que o libuv moderno faz,
   mas não verifiquei o fonte do libuv desta versão do Node. Confiança MEDIUM. O teste da §7
   imprime `os.release()` ao lado do `winver` justamente para fechar isso.
4. **Se ativa mas só chega silêncio, dá para distinguir "Windows desatualizado" de "nada está
   tocando"?** Não, e no modo EXCLUIR isso é pior, porque silêncio é o estado normal. O watchdog
   avisa; ele não diagnostica. Aceite.

### Passo 1 — o build exato, com revisão (PowerShell)


Esperado numa máquina que passa: `CurrentBuild` ≥ 19041 e `UBR` alto (milhares). O `UBR` é
justamente o que o `os.release()` não mostra.

### Passo 2 — o teste que decide (não precisa de Electron, nem do app)

Isto responde **"este Windows ativa o process loopback em modo EXCLUIR?"**, que é uma pergunta
sobre o **sistema operacional** — e para essa pergunta o `node.exe` é ambiente suficiente
(o `.node` é N-API com delay-load e carrega nos dois hospedeiros). O que o `node.exe`
**não** responde é se o addon carrega dentro do `electron.exe` — mas isso já foi respondido: o
build do app já externaliza `require("loopback-capture")` e essa parte é do checkpoint 08.6-06.

```powershell
mkdir $env:TEMP\lb-test; cd $env:TEMP\lb-test
npm init -y | Out-Null
npm i loopback-capture@2.0.0
```

`teste.cjs` (salve no mesmo diretório):

```js
const os = require('node:os')
const { LoopbackCapture } = require('loopback-capture')

// Troque para true e rode de novo se o EXCLUDE falhar: distingue
// "esta máquina não faz process loopback" de "não faz o modo EXCLUIR".
const INCLUIR = false

console.log('node        ', process.version)
console.log('os.release()', os.release(), '(compare com o winver do passo 1)')
console.log('pid         ', process.pid, '| modo:', INCLUIR ? 'INCLUIR' : 'EXCLUIR')

const cap = new LoopbackCapture()
let chunks = 0, bytes = 0

try {
  cap.start(process.pid, INCLUIR, (b) => { chunks++; bytes += b.length })
} catch (e) {
  console.error('\n>>> ATIVACAO FALHOU. Esta linha inteira e a resposta:')
  console.error(e.message)   // "Failed to start loopback capture (HRESULT 0x...)"
  process.exit(1)
}

console.log('\nstart() NAO lancou. Ponha musica/video para tocar AGORA (10s)...')
setTimeout(() => {
  console.log(`\nchunks=${chunks}  bytes=${bytes}  (~${(bytes / 192000).toFixed(1)}s de audio)`)
  console.log(chunks > 0
    ? '>>> FUNCIONA. O portao de 20348 estava errado nesta maquina.'
    : '>>> ATIVOU MAS NAO CHEGOU NADA. Rode o Windows Update ate o fim e repita.')
  cap.stop()
  process.exit(chunks > 0 ? 0 : 2)
}, 10000)
```

```powershell
node teste.cjs
```

**Como ler o resultado:**

| Saída | Significado | O que fazer |
|---|---|---|
| `FUNCIONA` com `INCLUIR = false` | modo EXCLUIR ativo em Windows 10 | **Troque o 20348 por 19041 e siga.** Resposta completa. |
| `ATIVACAO FALHOU` com um HRESULT | anote o HRESULT e rode de novo com `INCLUIR = true` | se o INCLUIR funcionar: o problema é o modo EXCLUIR, não o Windows — e isso afeta o Windows 11 também. Se os dois falharem: veja o HRESULT antes de qualquer conclusão. |
| `ATIVOU MAS NAO CHEGOU NADA` | é o modo de falha que o README do `win-capture-audio` descreve, **ou** nada estava tocando | confirme que havia som saindo pelo dispositivo padrão, rode `Windows Update` até não oferecer mais nada, reinicie e repita |
