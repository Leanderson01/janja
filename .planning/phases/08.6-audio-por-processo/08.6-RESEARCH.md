# Fase 8.6: Áudio de compartilhamento por processo — Pesquisa

**Pesquisado:** 2026-08-25
**Domínio:** WASAPI process loopback (Windows) + ponte PCM → WebRTC via LiveKit, dentro de Electron 43
**Confiança geral:** MEDIUM-HIGH — o caminho está verificado no código-fonte e no binário publicado; **nada disso foi executado**, porque este ambiente é WSL2 sem Windows, sem placa de som e sem `desktopCapturer` real (ver §11)

---

## 1. Resumo executivo

A Fase 8 apostou numa constraint (`restrictOwnAudio`) e perdeu. A Fase 8.6 não precisa de
constraint nenhuma: **o Windows sabe capturar "tudo que o sistema toca, MENOS a árvore de
processos do Hydra"**, e é isso que elimina o eco por construção — do mesmo jeito que o FIX
de 2026-08-25 eliminou por não conceder o loopback, só que agora com som.

O achado que muda o plano inteiro: **o pacote `loopback-capture` EXPÕE o modo de EXCLUIR**,
apesar de o README não mencionar. O terceiro parâmetro documentado como
`includeProcessTree: boolean` é passado direto para
`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE : PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`
no C++ (verificado no `.tgz` publicado, `package/src/LoopbackCapture.cpp:89`). Ou seja:
`capture.start(process.pid, false, cb)` = "capture o sistema inteiro, tirando o Hydra e
seus filhos".

Isso derruba três perguntas do ROADMAP de uma vez:
- **não precisa de HWND → PID** (pergunta 3) — não há processo alvo a descobrir;
- **não existe o problema de processos filhos** (pergunta 5) — a exclusão já é por árvore, e
  o navegador com processo por aba é justamente o caso em que o modo INCLUIR falha;
- **tela inteira TEM áudio** (a pergunta explícita do prompt) — é o mesmo caminho de código
  que o compartilhamento de uma janela, sem ramo especial.

O preço honesto: com EXCLUIR, o que vai para a call é **tudo que o computador toca** (o jogo,
mas também o Spotify, o vídeo da outra aba, a notificação do Windows), menos o Hydra. Não é o
comportamento do Discord — é o comportamento do OBS "Desktop Audio" com o app removido. É uma
troca de escopo por robustez, e ela precisa aparecer no texto do toggle.

**Recomendação primária:** `loopback-capture@2.0.0` no processo main, **modo EXCLUIR com o PID
do próprio main**, PCM 16-bit/48 kHz/estéreo → IPC → `AudioWorklet` + `MediaStreamAudioDestinationNode`
no renderer → `publishTrack(..., { source: Track.Source.ScreenShareAudio, forceStereo: true })`.
`audio: 'loopback'` do Electron **nunca mais é concedido**.

### 3.2 O modo EXCLUIR existe (o achado que decide a fase)

`package/src/LoopbackCapture.cpp:89` — no tarball publicado, não só no GitHub:

```cpp
audioclientActivationParams.ProcessLoopbackParams.ProcessLoopbackMode = includeProcessTree ?
    PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE : PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE;
audioclientActivationParams.ProcessLoopbackParams.TargetProcessId = processId;
```

E o wrapper N-API repassa o booleano sem tocar (`package/src/LoopbackCaptureWrap.cpp`,
`Start()`): `bool includeProcessTree = info[1].As<Napi::Boolean>().Value();`.

**Portanto `capture.start(process.pid, false, cb)` é o modo excluir**, e está disponível hoje,
via API pública, sem fork. O README apenas não conta.

> Confiança: **HIGH** de que a chamada existe e chega ao Windows.
> **MEDIUM** de que ela FUNCIONA como esperado — o modo excluir é muito menos rodado no mundo
> real que o incluir (OBS e Discord usam INCLUIR). Só sobe para HIGH com um teste no Windows do Leo.

### 3.3 Formato e comportamento do fluxo

`package/src/LoopbackCapture.cpp:171-175` — formato **fixado no código**, não negociado:

```cpp
m_CaptureFormat.wFormatTag     = WAVE_FORMAT_PCM;
m_CaptureFormat.nChannels      = 2;
m_CaptureFormat.nSamplesPerSec = 48000;
m_CaptureFormat.wBitsPerSample = 16;
```

Fixar o formato é **correto e proposital**: `GetMixFormat()` retorna `E_NOTIMPL` no dispositivo
virtual de process loopback (bug conhecido e documentado na Microsoft Q&A). O pacote contorna
pedindo `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM` (linha 182). Ou seja: **essa armadilha clássica já
está resolvida dentro do pacote** — não é trabalho do plano.

**Armadilha que NÃO está resolvida — buffers silenciosos são DESCARTADOS**
(`package/src/LoopbackCapture.cpp:514`):

```cpp
if (m_DeviceState != DeviceState::Stopping && !IsBufferSilent(Data, FramesAvailable, &m_CaptureFormat, -70))
   EmitAudioData(...);
```

Consequências que o plano precisa absorver:
- **não existe callback durante o silêncio** — o consumidor não pode assumir fluxo contínuo nem
  usar a chegada de chunks como relógio;
- o limiar é **-70 dBFS**, então um fade-out muito baixo pode ser cortado antes do fim;
- para o pipeline recomendado isso é **benigno**: o ring buffer do `AudioWorklet` simplesmente
  produz zeros quando não há dado (é exatamente o que o silêncio deveria soar). Mas qualquer
  desenho que **concatene** chunks assumindo continuidade temporal está errado.

Outros detalhes lidos no wrapper que o plano precisa conhecer:
- `stop()` **bloqueia a thread que chama** até a fila do Media Foundation confirmar a parada
  (comentário explícito em `LoopbackCaptureWrap.cpp`). No processo main isso bloqueia o event
  loop por dezenas de ms. Não é fatal; é motivo para não chamar `stop()` dentro de um caminho
  sensível a latência (e é um argumento a favor do `utilityProcess`, §6.4).
- Uma instância = uma captura. `start()` numa instância já iniciada **lança**
  (`"Capture already started on this instance"`). Criar `new LoopbackCapture()` por transmissão.
- Entrega via `Napi::ThreadSafeFunction` com fila ilimitada e `NonBlockingCall`; em falha o
  chunk é **descartado em silêncio** (comentário no `EmitAudioData`). Sem contrapressão, sem erro.
- `startSystemAudio(cb)` existe e é **loopback de dispositivo clássico** — ou seja, **o eco de
  volta**. Nunca usar como fallback (§9).

## 4. Compatibilidade com Electron 43 — por que não precisa de rebuild

Verificado no binário publicado, com `objdump -p`/`strings` sobre
`package/build/Release/loopback_capture_addon.node`:

| Fato observado | O que significa |
|---|---|
| `PE32+ executable (DLL) x86-64, for MS Windows` | x64 Windows. Nada para ARM64 — irrelevante hoje, mas é um limite real. |
| Símbolos `napi_*` presentes; `CMakeLists.txt` define `-DNAPI_VERSION=4` | **N-API**, não NAN/V8. ABI estável entre runtimes: um binário N-API v4 carrega em qualquer runtime com N-API ≥ 4. Electron 43 = **Chromium 150 / Node 24.17** → N-API 10. |
| `node.exe` aparece na **Delay Import Directory**, não nos imports normais | É o `win_delay_load_hook` (entra pelo `${CMAKE_JS_SRC}` do CMakeLists). É exatamente o mecanismo que redireciona os símbolos para o executável hospedeiro — `electron.exe` em vez de `node.exe`. Sem ele, o addon só carregaria sob o Node. |
| Imports: só `api-ms-win-core-*`, `MMDevAPI.DLL`, `MFPlat.DLL` | **Nenhum `vcruntime140.dll` / `msvcp140.dll`** → CRT estático → **não exige o Visual C++ Redistributable** na máquina de quem instala. Isso é uma ausência de dor de cabeça que vale registrar. |
| Sem `binding.gyp`, sem `prebuilds/` | `@electron/rebuild` (usado pelo `install-app-deps`) detecta módulo nativo por `binding.gyp` / `prebuilds/` / `node-pre-gyp`. Não achando nenhum, **pula**. O `scripts/postinstall-rebuild.mjs` continua valendo como está, sem mudança. |

> **Confiança: HIGH** de que o binário é compatível por construção.
> **O que só a máquina do Leo prova:** que `require('loopback-capture')` de fato carrega no
> Electron 43 no Windows dele. Um `node -e` não serve (Pitfall do HANDOFF §1: "verificar no
> ambiente errado não é verificar") — tem que ser `electron`.

| Fonte | Requisito declarado |

| README do `loopback-capture` | "Windows 10 x64 and later" (otimista demais; ignorar) |

Leitura honesta: **build 20348 é o número oficial, e ele é maior que qualquer build de Windows
10 de consumidor** (o 22H2 é 19045). Na prática o recurso é **Windows 11**, com uma zona cinzenta
de Windows 10 2004+ totalmente atualizado onde relatos dizem que funciona. Não há como decidir
isso por leitura — é empírico, por máquina.

**Consequência para o plano:** a fase precisa de um **portão + uma degradação honesta**, não de
uma suposição:

1. Portão barato antes de tentar: `os.release()` no Windows devolve `"10.0.<build>"`; comparar
   o build com 20348. Confiança MEDIUM (o libuv moderno usa `RtlGetVersion`, que não mente por
   manifesto — mas não testei).
2. Portão que vale de verdade: **tentar** `start()` e tratar a falha. `Start()` lança
   `Error("Failed to start loopback capture (HRESULT 0x...)")` quando a ativação falha — é o
   sinal certo, e o HRESULT deve ir para o log.
3. Terceiro modo de falha, o pior: **inicia sem erro e só chegam zeros** (é o que a issue #414
   do `Windows-classic-samples` descreve com o Teams). Precisa de um detector de "nenhum chunk
   em N segundos" para virar aviso na UI, e não silêncio inexplicado.

Se o portão fechar: **compartilha sem áudio, com a mesma honestidade do FIX atual** — o toggle
aparece desabilitado com "Seu Windows não suporta áudio por aplicativo (precisa do Windows 11)".

### 6.2 O caminho recomendado, concretamente

```
[main] loopback-capture  -> Buffer PCM s16le estéreo 48k (~10 ms por chunk, ~192 KB/s)
   |  webContents.send (canal novo, uma via)      <- ~100 mensagens/s, payload ~1.9 KB
[renderer] preload expõe onScreenShareAudioChunk(cb)
   -> port.postMessage(ArrayBuffer transferível) para um AudioWorkletProcessor
   -> ring buffer Float32 no worklet (s16 -> float: amostra / 32768)
   -> AudioWorkletNode.connect(MediaStreamAudioDestinationNode)
   -> dest.stream.getAudioTracks()[0]
   -> room.localParticipant.publishTrack(track, {
        source: Track.Source.ScreenShareAudio,
        forceStereo: true,
        dtx: false, red: false,
        audioPreset: AudioPresets.musicHighQualityStereo,
        stream: <mesmo nome de stream da track de vídeo, para sincronizar>
      })
```

Pontos que decidem se isto funciona ou vira ruído:

- **`new AudioContext({ sampleRate: 48000, latencyHint: 'interactive' })`.** Sem fixar o
  `sampleRate`, o contexto adota a taxa do dispositivo de saída (44,1 kHz existe no mundo real)
  e você passa a precisar de reamostragem. Fixando 48000 — a mesma taxa que o addon entrega —
  a conversão é uma multiplicação por amostra e nada mais.
- **Deriva de relógio (drift):** com loopback de dispositivo os dois lados são o MESMO relógio
  (o do dispositivo de saída) e a deriva é ~zero. Com **process loopback** a captura vem de um
  dispositivo *virtual*, e não achei documentação dizendo a que relógio ele está preso.
  Trate como desconhecido: o ring buffer precisa de política de saturação (descartar o mais
  antigo) e de fome (emitir zeros), nunca de crescimento sem limite. Confiança: LOW —
  **só medindo em Windows** (contar amostras entregues vs. tempo do `AudioContext` por 10 min).
- **Nada de `SharedArrayBuffer`** como premissa: no Electron ele depende de isolamento
  cross-origin, e este app não é cross-origin isolated. `port.postMessage` com `ArrayBuffer`
  transferível resolve sem nenhuma flag.
- **Alvo do buffer: 40–80 ms.** Menos que isso e cada engasgo do IPC vira clique; mais que isso
  e o áudio descola visivelmente do vídeo.

**Latência somada, estimada (não medida):** ~10 ms (pacote WASAPI) + ~1 ms (IPC) + 40–80 ms
(ring buffer) + ~10 ms (render quantum + encoder) ≈ **60–100 ms** acima do caminho de hoje.
Para áudio de transmissão isso é invisível; para conversa seria demais. Confiança: MEDIUM.

### 6.3 A alternativa mais curta, que eu NÃO recomendo como base

`MediaStreamTrackGenerator({ kind: 'audio' })` + `writer.write(new AudioData({ format: 's16', sampleRate: 48000, ... }))`
eliminaria o `AudioContext`, o worklet e o ring buffer — timestamps explícitos, zero
reamostragem, ~30 linhas a menos.

Por que não como base: o Chrome Platform Status só reconhece hoje a forma **`VideoTrackGenerator`**
("the WG-agreed form of the interface that was previously known as MediaStreamTrackGenerator,
specialized for video"), e a especificação registra que **não há consenso do WG sobre suportar
áudio**. Em Chromium 150 pode existir, pode estar atrás de flag, pode ter sumido — não consegui
confirmar. **Confiança: LOW.**

Encaminhamento certo: `AudioWorklet` como caminho único; se alguém quiser o generator, que seja
um `if (typeof MediaStreamTrackGenerator !== 'undefined')` **medido no Windows primeiro** e
tratado como otimização opcional, nunca como o caminho que o plano depende.

### 6.4 Onde o addon deve rodar

| Opção | A favor | Contra |
|---|---|---|
| **Processo main** (recomendado p/ v1) | Simples; mesmo lugar do `screenshare.ts`; `process.pid` já é a raiz da árvore a excluir | `stop()` bloqueia o event loop do main por dezenas de ms; crash do addon derruba o app inteiro |
| `utilityProcess` + `MessagePortMain` para o renderer | Isola crash e o `stop()` bloqueante; o PCM vai direto ao renderer sem passar pelo main | Mais peças; o PID a excluir passa a ser o do main (tem que ser passado, não lido de `process.pid`) |
| Preload (`sandbox: false` permite `require`) | Zero salto de processo | Código nativo dentro do processo do renderer; é o processo que mais morre e mais recarrega. **Não.** |

192 KB/s e ~100 mensagens/s por IPC é carga trivial — não é o `utilityProcess` que se justifica
por desempenho, e sim por isolamento. **Comece no main; o `utilityProcess` é a evolução se o
`stop()` bloqueante ou um crash aparecerem no uso real.**

## 7. Tela inteira, e por que INCLUIR não é o caminho — resposta explícita

**Pergunta:** o que fazer quando o usuário compartilha a TELA INTEIRA, que não tem processo alvo?

**Resposta:** **nada de especial — e ela TEM áudio.** No modo EXCLUIR não existe "processo alvo"
a descobrir: o alvo é sempre o *nosso* processo, e o que se captura é todo o resto. Janela e tela
inteira usam **exatamente o mesmo código**. Esta é a razão principal para escolher EXCLUIR e não
INCLUIR, acima de qualquer outra.

Para registro, a comparação que sustenta a decisão:

| | EXCLUIR o Hydra (recomendado) | INCLUIR o app alvo (o que o Discord faz) |
|---|---|---|
| Compartilhar UMA janela | Funciona. Vai junto o áudio de outros apps. | Funciona e é mais preciso. |
| Compartilhar a TELA INTEIRA | **Funciona.** | **Sem áudio** — não há PID para mirar. Seria preciso um segundo caminho, que é justamente o EXCLUIR. |
| Descobrir o PID a partir da janela | Não precisa. | Precisa de `GetWindowThreadProcessId` (nativo) e ainda de tratamento para UWP/`ApplicationFrameWindow`. |
| App com muitos processos (navegador) | Indiferente. | Frágil: o áudio do Chromium sai do processo utilitário de áudio, filho do processo-navegador — a árvore salva **se** você acertou o processo-navegador, e o `desktopCapturer` te dá o dono da JANELA. |
| Eco da call | Eliminado por construção (o Hydra e seus filhos estão fora, e é o Hydra que toca a voz dos outros). | Eliminado por construção (só o alvo entra). |
| Vazamento indesejado | **Sim:** Spotify, notificações, outra aba. Precisa estar escrito no toggle. | Não. |
| Rodagem no mundo real | Menor. OBS e Discord usam INCLUIR. | Maior. |

**Se um dia o INCLUIR for necessário**, as três saídas para HWND → PID, com o custo de cada uma:

1. **`electron-native-screenshare`** (npm, 1.2.0, 2026-08-09) — tem `getPidFromWindowHandle(hwnd)`
   com tratamento de UWP, **e** os dois modos. Mas `"install": "node-gyp rebuild"`, **sem
   prebuilds**: exigiria Visual Studio Build Tools em toda máquina que rodar `npm install`.
   Isso contradiz frontalmente a decisão registrada no topo de `scripts/postinstall-rebuild.mjs`
   ("não é algo que se possa presumir que exista na máquina de quem só quer gerar o instalador").
   **Rejeitado por isso, não pela API — a API dele é a melhor das três.**
2. **FFI (`koffi`)** para chamar `GetWindowThreadProcessId` de `user32.dll` — duas linhas, mas é
   mais uma dependência nativa e uma superfície de FFI aberta dentro do app.
3. **Addon próprio.** Custo honesto: ~40 linhas de C++ (é literalmente uma chamada de Win32),
   mais `binding.gyp`, mais **toolchain de compilação no CI para gerar o prebuild**, mais o
   trabalho de empacotar e versionar. O código é trivial; **o pipeline de build é que custa** —
   e é exatamente a dor que o `postinstall-rebuild.mjs` documenta que este projeto não quer.
   Um addon próprio só se paga se o modo INCLUIR virar requisito de produto.

## 8. Empacotamento — o precedente do `uiohook-napi` e as duas diferenças

O que se repete do precedente:

```yaml
# electron-builder.yml
asarUnpack:
  - resources/**
  - node_modules/uiohook-napi/**
  - node_modules/loopback-capture/**     # novo
```

O que **NÃO** se repete, e é onde este plano pode quebrar o instalador:

**(a) `bindings` resolve pelo stack trace — bundlar mata.**
`package/dist/index.cjs` chama `bindings({ try: [["module_root","build","Release","loopback_capture_addon.node"], ...] })`.
O `bindings` descobre o `module_root` inspecionando o `Error.stack` para achar o arquivo que o
chamou e subindo diretórios até um `package.json`. Se o electron-vite **inline**ar o pacote
dentro de `out/main/index.js`, o chamador vira o bundle, o `module_root` vira a **raiz do app**,
e ele procura o `.node` em `app.asar/build/Release/` — que não existe. Falha em runtime, no
Windows, só no app empacotado.

Estado atual, **verificado no artefato construído** (`out/main/index.js`): os requires
sobreviventes são exatamente `@electron-toolkit/utils`, `@workos-inc/node`, `electron`, `fs`,
`path`, `uiohook-napi` — ou seja, **o electron-vite já externaliza dependências**, e
`loopback-capture` seguiria o mesmo caminho. Mas isso é um comportamento herdado de um
`main: {}` vazio em `electron.vite.config.ts`. O plano deve **verificar (grep no bundle), não
supor** — e considerar tornar explícito (`build.rollupOptions.external`).

**(b) `cmake-js` é dependência de RUNTIME do pacote.**
`package.json` do `loopback-capture`: `"dependencies": { "bindings", "cmake-js", "node-addon-api" }`.
O `cmake-js` é ferramenta de build, mas está em `dependencies` — e o electron-builder empacota
`dependencies`. Ele arrasta `rc, tar, debug, which, yargs, semver, fs-extra, url-join, node-api-headers`.
Nada disso é usado em runtime (`dist/index.cjs` só requer `bindings` e `node:os`).
Excluir no `files` do electron-builder é seguro **e** deve ser feito conscientemente:

```yaml
files:
  - '!node_modules/cmake-js/**'
```

**(c) O que NÃO muda:** `npmRebuild: false` continua correto, e o `postinstall-rebuild.mjs` não
precisa de alteração — sem `binding.gyp`, o `@electron/rebuild` não tem por onde tentar
recompilar este pacote.

## 9. Armadilhas (o que vai dar errado se ninguém escrever isso no plano)

### Armadilha 1 — Reintroduzir o eco pela porta dos fundos
`loopback-capture` tem `startSystemAudio(cb)`, que é **loopback de dispositivo** — o mesmo
mecanismo do `audio: 'loopback'` do Electron, com o mesmo eco. Ele parece um fallback natural
("se o process loopback falhar, use o do sistema") e **é uma armadilha perfeita**: funciona em
qualquer Windows, entrega áudio, e devolve o defeito de 2026-08-20 para 4 pessoas numa call.
**Regra do plano: `startSystemAudio` não é chamado em lugar nenhum.** O fallback de "não deu"
é *sem áudio*, exatamente como hoje.

### Armadilha 2 — `audio: 'loopback'` continuar concedível
A concessão em `src/main/screenshare.ts` (`callback(grantLoopback ? { video, audio: 'loopback' } : { video })`)
deve virar **incondicionalmente** `callback({ video: chosen.source })`. Se sobrar um caminho em que
ela é concedida, o eco volta por ali. `loopbackWithMute` (a outra string aceita pelo Electron,
`electron.d.ts:23719-23723`) **não serve**: ela silencia a reprodução local do dispositivo — ou
seja, quem compartilha para de ouvir a call.

### Armadilha 3 — Publicar mono sem perceber
Se `getSettings().channelCount` não vier na track do `MediaStreamAudioDestinationNode`, o SDK
decide mono (`30067`), e ninguém recebe erro. Passar `forceStereo: true` e **verificar no
`RTCRtpSender.getParameters()`/SDP** que saiu `stereo=1`.

### Armadilha 4 — Track publicada com `source: unknown`
Publicar o `MediaStreamTrack` sem `{ source: Track.Source.ScreenShareAudio }` custa três coisas
de uma vez: o `setScreenShareEnabled(false)` **não** despublica junto (`29822`), o republish
pós-reconexão tenta reiniciar a track (`30743`), e o lado remoto não sabe agrupar com o vídeo.

### Armadilha 5 — Deixar a captura nativa viva depois do fim
O SDK dá `track.stop()` na track do destination ao despublicar (`30646`), mas **não sabe nada**
do `loopback-capture` nem do `AudioContext`. Sem um gancho explícito, o WASAPI continua
capturando e o processo continua recebendo 100 callbacks/s para sempre. É o Pitfall 2 da Fase 8
com outra roupa: todo caminho de saída (parar, cancelar, sala desconectar, janela fechar, track
de vídeo terminar sozinha) precisa terminar em `capture.stop()` + `audioContext.close()`.

### Armadilha 6 — Alguns apps simplesmente não aparecem
Issue **#414** do `microsoft/Windows-classic-samples`: a amostra oficial captura **silêncio** do
Microsoft Teams — buffers de duração e formato corretos, cheios de zeros — e o relator diz que
falha **nos dois modos**, enquanto o loopback de dispositivo captura o mesmo áudio normalmente.
Não há causa raiz publicada (a pista é o Teams manter duas sessões de render). Tratar como
verdade do mundo: **existe app cujo áudio não entra no process loopback**, e o produto precisa
falhar de forma legível ("não chegou áudio nenhum") em vez de mudo e sem explicação.

### Armadilha 7 — Crash em jogo de tela cheia exclusiva
Microsoft Q&A (Windows 11 22H2): a amostra oficial sofre *access violation* em
`OnAudioSampleRequested()` quando o alvo é um jogo em fullscreen exclusivo e o usuário faz
Alt+Tab; a Microsoft reconheceu e não publicou contorno. É um crash **dentro do processo que
hospeda o addon** — mais um argumento para o `utilityProcess` se o público for gamer.

### Armadilha 8 — Não assumir fluxo contínuo
Ver §3.3: silêncio não gera callback. Qualquer medição de "está funcionando?" baseada em
"chegaram chunks" precisa de janela de tolerância, ou vai acusar falha num momento de silêncio.

## 11. O que este ambiente NÃO pode provar

WSL2: sem Windows, sem placa de som, sem `desktopCapturer` real, sem `electron.exe`. **Zero** do
caminho nativo é testável aqui. Concretamente, só se prova na máquina do Leo:

1. Que `require('loopback-capture')` carrega **no Electron 43** (não no Node) no Windows dele.
2. Que `start(pid, false, cb)` **não lança** — e, se lançar, qual HRESULT (é o número que
   distingue "Windows velho demais" de "outra coisa").
3. Que **chegam chunks** e que o áudio é o certo — e, principalmente, que **a voz dos outros
   participantes NÃO está lá**. Este é o teste da fase inteira; precisa de 3+ pessoas na call.
4. Que sobrou áudio do que se queria: compartilhar um vídeo e ouvir o vídeo do outro lado.
5. Que a tela inteira se comporta igual à janela.
6. Deriva de relógio em 10+ minutos de transmissão contínua.
7. Que o instalador NSIS gerado carrega o `.node` de dentro de `app.asar.unpacked`.
8. Que o build do Windows do usuário passa do portão 20348 — e o que acontece com quem não passa.

O que **é** testável aqui, e deve ser onde os testes moram: conversão s16→float, ring buffer
(fome, saturação, ordem), parsing do build do `os.release()`, sanitização do payload do IPC, e o
`publishTrack` contra um LiveKit mockado. Mesma divisão do resto do projeto.

## 12. Decisão recomendada, em uma linha cada

- **Caminho:** `loopback-capture@2.0.0` no processo main, **modo EXCLUIR** com o PID do main,
  um único código para janela e tela inteira, PCM → `AudioWorklet` → `MediaStreamDestination` →
  `publishTrack(..., { source: ScreenShareAudio, forceStereo: true })`.
- **Alternativa nomeada:** modo INCLUIR por PID da janela (comportamento do Discord), que exige
  HWND→PID — hoje só disponível em pacote que compila na instalação (`electron-native-screenshare`)
  ou em addon próprio.
- **Critério que decide entre os dois:** se, no uso real, o vazamento de áudio alheio (Spotify,
  notificação, outra aba) incomodar mais do que a ausência de áudio na tela inteira incomodaria.
  Enquanto ninguém reclamar, EXCLUIR ganha por ser um caminho só.
- **Custo honesto da fase:** uma dependência nativa nova (pré-compilada, sem toolchain), duas
  armadilhas de empacotamento (`bindings`+bundler, `cmake-js` em `dependencies`), um recurso que
  **só existe de Windows 11 para cima** — com degradação para "sem áudio" abaixo disso — e um
  pipeline de áudio novo cuja correção **não pode ser verificada fora do Windows**.
- **O que NÃO fazer:** `startSystemAudio()` como fallback (é o eco de volta), `loopbackWithMute`
  (silencia a call de quem compartilha), e depender de `MediaStreamTrackGenerator` para áudio.
