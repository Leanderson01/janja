<objective>
Trazer a dependência nativa `loopback-capture@2.0.0` para o projeto e fechar,
de uma vez, as três armadilhas de empacotamento que a pesquisa identificou —
antes de qualquer linha de captura existir. Empacotamento é parte desta fase,
não follow-up: as três falham SÓ no instalador, no Windows, nunca em dev e
nunca em teste.

Purpose: o precedente do `uiohook-napi` (Fase 9) resolve metade do problema
(`asarUnpack`), e a outra metade é nova. `loopback-capture` usa `bindings`,
que localiza o `.node` inspecionando o `Error.stack` para descobrir qual
arquivo o chamou e subir diretórios até achar um `package.json`. Se o
electron-vite inlinar o pacote dentro de `out/main/index.js`, o chamador vira
o bundle, o `module_root` vira a raiz do app, e ele procura o binário em
`app.asar/build/Release/` — que não existe. Além disso o pacote declara
`cmake-js` (ferramenta de BUILD) em `dependencies`, e o electron-builder
empacota `dependencies`.
Output: dependência instalada e pinada, configuração de build ajustada, e um
script de verificação no estilo de `scripts/verify-renderer-runtime.mjs` que
transforma cada uma dessas armadilhas em falha de build ruidosa.
</objective>

  <name>Task 1: Instalar e pinar loopback-capture, com a verdade sobre o que ele traz</name>
  <files>package.json, package-lock.json</files>
  <action>
    Instalar com versão EXATA (sem `^`), porque o pacote tem uma única versão
    publicada, um mantenedor e ~525 downloads/mês — uma API que pode mudar sem
    aviso não deve entrar por faixa:

        npm install --save-exact loopback-capture@2.0.0

    Confirmar, e registrar no SUMMARY, cada um destes fatos POR EXECUÇÃO (não
    por leitura da pesquisa — os comandos abaixo rodam em WSL2 e todos são
    verificáveis aqui):

    1. `node -e "const p=require('./node_modules/loopback-capture/package.json'); console.log(p.version, JSON.stringify(p.scripts))"`

       `scripts/postinstall-rebuild.mjs` NÃO precisa de alteração nenhuma
       nesta fase. Confirmar rodando `npm run postinstall` e verificando que
       o `.node` continua lá, intacto (mesmo `md5sum` antes e depois).
    4. Rodar `npm install` inteiro e confirmar exit 0 em WSL2 — o pacote não
       tem campo `os`/`cpu` restringindo a plataforma (confirmado no
       packument), então a instalação funciona em Linux; o que não funciona
       em Linux é CARREGAR o `.node`, e isso é tratado no Plano 08.6-02.

    Acrescentar ao `package.json`, junto da entrada nova, NADA de scripts
    ainda — o script de verificação entra na Task 3.

    plano. Nenhum arquivo de `src/` é tocado aqui.

<task type="auto">
  <name>Task 2: Fechar as três armadilhas na configuração de build</name>
  <files>electron-builder.yml, electron.vite.config.ts</files>
  <action>
    **(a) `electron-builder.yml` — desempacotar o addon do asar.**
    Acrescentar ao bloco `asarUnpack` existente, ao lado de `uiohook-napi`:

        - node_modules/loopback-capture/**

    Motivo, em comentário no arquivo: um `.node` dentro de `app.asar` não pode
    ser carregado por `LoadLibrary` — o Windows precisa de um caminho de
    arquivo real, e `app.asar.unpacked/` é onde ele fica.

    **(b) `electron-builder.yml` — não empacotar a ferramenta de build.**
    Acrescentar ao bloco `files`:

        - '!node_modules/cmake-js/**'

    `cmake-js` está em `dependencies` do `loopback-capture` (não em
    `devDependencies`), e o electron-builder empacota `dependencies`. Ele é
    ferramenta de compilação e não é requerido por `dist/index.cjs`, que só
    requer `bindings` e `node:os` — confirmar isso por execução antes de
    excluir:

        grep -o "require(\"[^\"]*\")" node_modules/loopback-capture/dist/index.cjs | sort -u

    Depois de excluir, rodar `npm run build:unpack` (que gera
    `dist/linux-unpacked` neste ambiente) e MEDIR o que entrou:

        find dist/*-unpacked/resources -name 'cmake-js' -o -name 'node-api-headers' | head

    Se transitivas exclusivas do `cmake-js` (`rc`, `url-join`,
    `node-api-headers`) ainda aparecerem, acrescentar exclusões para elas
    também — uma linha por pacote MEDIDO, nunca por suposição, e cada uma
    justificada em comentário com o resultado do `find`. NÃO excluir `bindings`
    nem `node-addon-api`: `bindings` é requerido em runtime.

    **(c) `electron.vite.config.ts` — tornar a externalização EXPLÍCITA.**
    Hoje o bloco `main` é `{}` e as dependências ficam externas por herança de
    comportamento do electron-vite (verificado: `out/main/index.js` só tem
    `require` de `@electron-toolkit/utils`, `@workos-inc/node`, `electron`,
    `fs`, `path`, `uiohook-napi`). Herança de comportamento não é contrato.
    Trocar por:

        main: {
          build: {
            rollupOptions: {
              external: ['loopback-capture', 'uiohook-napi']
            }
          }
        }

    Comentário obrigatório acima, explicando que inlinar `loopback-capture`
    quebra o `bindings` (que resolve o `.node` pelo `Error.stack`) e que a
    falha aconteceria só no app empacotado, no Windows.

    **(d) `electron.vite.config.ts` — impedir que o worklet de áudio seja
    inlinado como data: URI.** O Plano 08.6-03 vai carregar um
    `AudioWorkletProcessor` a partir de um arquivo `.js` emitido como asset
    (`import url from './...js?url'`). A CSP deste app é
    `script-src 'self'` (ver `src/renderer/index.html`) — um `data:` URI ou um
    `blob:` seria BLOQUEADO pelo Chromium, e o sintoma seria "sem áudio" sem
    erro de aplicação, exatamente a lição nº 2 do HANDOFF (a CSP do template
    bloqueando o WebSocket do Convex). O Vite inlina assets abaixo de 4 KB por
    padrão, e o worklet é pequeno. No bloco `renderer`, acrescentar:

        build: { assetsInlineLimit: 0 }

    com comentário explicando exatamente isso.

    NÃO tocar na CSP do `index.html` neste plano nem em nenhum outro desta
    fase: `script-src 'self'` continua como está, e é o caminho de asset que
    se adapta a ela — não o contrário.
  </action>
  <verify>
    `npm run build` exit 0; `grep -c 'loopback-capture' electron-builder.yml electron.vite.config.ts` > 0 em ambos;
    `npm run build:unpack` exit 0 e `find dist/*-unpacked/resources -path '*cmake-js*' | wc -l` retorna 0;
    `grep -o 'require("[^"]*")' out/main/index.js | sort -u` continua sem novidades além das 6 conhecidas.
  </verify>
  <done>
    `asarUnpack` cobre `loopback-capture`, `cmake-js` (e transitivas medidas)
    fora do pacote, `external` explícito no main, `assetsInlineLimit: 0` no
    renderer — cada um com o comentário que explica qual falha ele previne.
  </done>
</task>

<task type="auto">
  <name>Task 3: Script de verificação que transforma as armadilhas em falha de build</name>
  <files>scripts/verify-native-audio-packaging.mjs, package.json</files>
  <action>
    Criar `scripts/verify-native-audio-packaging.mjs` no MESMO estilo de
    `scripts/verify-renderer-runtime.mjs` (cabeçalho longo explicando por que
    existe e qual defeito real ele impede; `process.exit(1)` com mensagem
    acionável; zero dependências além de `node:fs`/`node:path`).

    Quatro asserções, cada uma com mensagem de erro que diz o que fazer:

    1. **O addon não foi inlinado.** Ler `out/main/index.js`. Exigir que a
       string `require("loopback-capture")` esteja presente. Falhar se a
       string `loopback_capture_addon` aparecer no bundle (só apareceria se o
       `dist/index.cjs` do pacote tivesse sido inlinado).
    2. **O worklet virou arquivo, não data: URI.** Varrer `out/renderer/`
       procurando por um arquivo cujo nome comece com
       `screenshare-audio-processor` e termine em `.js`. Falhar se não achar.
       Falhar também se qualquer `.js` de `out/renderer/assets/` contiver a
       string `data:text/javascript` ou `data:application/javascript`.
       Esta asserção é TOLERANTE enquanto o Plano 08.6-03 não existir: se
       nenhum arquivo do renderer mencionar `screenshare-audio-processor`,
       emitir AVISO e passar. Assim que a string aparecer no bundle, a
       asserção passa a ser obrigatória. Implementar exatamente assim, com
       comentário — é o que permite este plano rodar na Onda 1.
    3. **O `.node` existe no node_modules** com tamanho > 100 KB (um arquivo
       de 0 byte por download interrompido é um modo de falha real).
    4. **`cmake-js` não está no bundle empacotado.** Se
       `dist/*-unpacked/resources/app.asar.unpacked` ou
       `dist/*-unpacked/resources/app` existir, verificar que não há
       `node_modules/cmake-js` dentro. Se `dist/` não existir (caso comum:
       ninguém rodou `--dir` ainda), pular com AVISO em vez de falhar.

    Acrescentar ao `package.json`:

        "verify:native-audio": "node scripts/verify-native-audio-packaging.mjs"

    e encaixar na cadeia de `build:win`, DEPOIS de `npm run build` e junto das
    outras verificações já existentes:

        "build:win": "npm run verify:build-env && npm run build && npm run verify:renderer-runtime && npm run verify:native-audio && npm run verify:no-secrets && electron-builder --win"

    O QUE ESTE SCRIPT NÃO PROVA, e precisa estar escrito no cabeçalho dele: que
    o `.node` CARREGA dentro do `electron.exe` no Windows, e que o instalador
    NSIS o coloca no lugar certo. Isso é item do checkpoint humano
    (08.6-06) — este script prova a forma, não o funcionamento.
  </action>
  <verify>
    `npm run verify:native-audio` exit 0 depois de `npm run build`;
    quebrar de propósito (renomear temporariamente o `.node`) faz sair exit 1 com mensagem legível — restaurar depois;
    `npm run build:win` NÃO precisa ser rodado aqui (exige Windows), mas `node -c` sobre o script e a leitura do package.json devem confirmar a cadeia.
  </verify>
  <done>
    `npm run verify:native-audio` existe, passa depois de um build limpo,
    falha de forma legível quando qualquer garantia é quebrada, e está na
    cadeia de `build:win`.
  </done>
</task>
