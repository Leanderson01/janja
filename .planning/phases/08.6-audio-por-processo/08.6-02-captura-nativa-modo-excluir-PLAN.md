<objective>
Ensinar o processo main a capturar "tudo que o computador toca, MENOS o Hydra
e seus filhos", e a entregar esse PCM ao renderer — ou a dizer, com motivo,
que não deu.

Purpose: é a metade nativa da fase. A pesquisa provou no C++ publicado
(`package/src/LoopbackCapture.cpp:89`) que o terceiro parâmetro de
`start(pid, includeProcessTree, cb)` mapeia direto para
`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` vs.
`PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`. Passando `false` com o
PID do próprio main, o Windows exclui a árvore inteira do app — e é o app que
toca a voz dos outros participantes. O eco morre por construção, e janela e
tela inteira usam exatamente o mesmo código, sem ramo especial.
Output: um módulo do main com contrato testado, e um arquivo de tipos sem
imports que o preload e o renderer podem consumir.
</objective>

        export const SCREENSHARE_AUDIO_CHANNELS = {
          /** renderer -> main, invoke: começa a captura; resolve com o resultado. */
          START: 'screenshare-audio:start',
          /** renderer -> main, uma via: para a captura. Idempotente. */
          STOP: 'screenshare-audio:stop',
          /** main -> renderer: um chunk de PCM cru. ~100/s. */
          CHUNK: 'screenshare-audio:chunk',
          /** main -> renderer: mudanças de estado (capturando, sem áudio, parou, falhou). */
          STATUS: 'screenshare-audio:status'

    Constantes, cada uma com o motivo em comentário:
    - `MIN_WINDOWS_BUILD_FOR_PROCESS_LOOPBACK = 20348` — o número oficial da
      Microsoft (`req.target-min-winverclnt` de `PROCESS_LOOPBACK_MODE`). É
      MAIOR que qualquer build de Windows 10 de consumidor (22H2 é 19045), ou
      seja: na prática o recurso é Windows 11, com uma zona cinzenta de
      Windows 10 2004+ totalmente atualizado onde há relatos de funcionamento
      (README do `win-capture-audio`). Por isso o portão de versão é a
      PRIMEIRA barreira, e nunca a única — a segunda é tentar e tratar a falha.
    - `SILENCE_WATCHDOG_MS = 15_000` — quanto tempo sem NENHUM chunk antes de
      avisar. Não pode ser curto: o addon DESCARTA buffers silenciosos
      (`IsBufferSilent`, limiar -70 dBFS, `LoopbackCapture.cpp:514`), então
      "nenhum chunk" durante um trecho quieto é comportamento normal, não
      falha. Ver a Armadilha 8 da pesquisa.

    Tipos:

        export type ScreenShareAudioFormat = {
          sampleRate: number      // 48000, fixado no C++ do pacote
          channels: number        // 2
          bitsPerSample: number   // 16, little-endian, intercalado
        }

        export type ScreenShareAudioUnavailableReason =
          | 'not-windows'      // WSL2/Linux/macOS: o recurso é Win32 puro
          | 'windows-too-old'  // build < 20348
          | 'addon-unavailable'// require falhou (arquitetura, .node ausente, asar)
          | 'start-failed'     // o addon lançou; `detail` carrega o HRESULT

        export type ScreenShareAudioCapability =
          | { supported: true }
          | { supported: false; reason: ScreenShareAudioUnavailableReason; detail?: string }

        export type ScreenShareAudioStartResult =
          | { ok: true; format: ScreenShareAudioFormat }
          | { ok: false; reason: ScreenShareAudioUnavailableReason; detail?: string }

        export type ScreenShareAudioStatus =
          | { kind: 'capturing' }
          | { kind: 'no-audio-yet' }   // watchdog: nada chegou em SILENCE_WATCHDOG_MS
          | { kind: 'stopped' }
          | { kind: 'failed'; reason: ScreenShareAudioUnavailableReason; detail?: string }

    `format` viaja no RESULTADO do start de propósito: o renderer não duplica
    48000/2/16 como constante própria — ele usa o formato que o main disse que
    está entregando. Duplicar seria criar duas fontes da verdade para um
    número que mora no C++ de terceiro.

    ------------------------------------------------------------------
    Comentário obrigatório, em caixa alta e no topo do arquivo:

    `startSystemAudio()` do pacote `loopback-capture` é PROIBIDO neste projeto.
    Ele é loopback de DISPOSITIVO — o mesmo mecanismo do `audio: 'loopback'` do
    Electron, com o mesmo eco que 4 pessoas viveram numa call em 2026-08-20.
    Ele parece um fallback natural ("se o process loopback falhar, use o do
    sistema") e é uma armadilha perfeita: funciona em qualquer Windows, entrega
    áudio, e devolve o defeito. O fallback de "não deu" é SEM ÁUDIO, com aviso
    na tela. Nunca loopback de dispositivo.
    ------------------------------------------------------------------

    **Carga do addon — preguiçosa e injetável.**
    NUNCA `import ... from 'loopback-capture'` no topo. Este projeto é
    desenvolvido em WSL2, e o `.node` é PE32+ do Windows: um import estático
    derrubaria o processo main em `npm run dev` aqui, todos os dias. Ao
    contrário do `uiohook-napi` (que publica prebuild de Linux e por isso pode
    ser importado no topo de `voice/ptt.ts`), este pacote só tem binário
    Windows x64.

        type LoopbackCaptureInstance = {
          start(processId: number, includeProcessTree: boolean, cb: (chunk: Buffer) => void): void
          stop(): void
        }
        type LoopbackCaptureModule = { LoopbackCapture: new () => LoopbackCaptureInstance }

    Um `let loadModule: () => LoopbackCaptureModule` com implementação padrão
    `() => require('loopback-capture')` e um export `__setModuleLoaderForTests`
    para os testes injetarem um fake. Usar `createRequire(import.meta.url)` se
    o bundle do main for ESM; conferir o formato de saída atual antes de
    escolher (o `out/main/index.js` de hoje usa `require`, então `require`
    direto basta — confirmar por leitura antes de escrever).

    **Portão de capacidade — `isProcessAudioSupported(): ScreenShareAudioCapability`.**
    Nunca lança. Em ordem, e parando no primeiro que reprovar:
    1. `process.platform !== 'win32'` -> `{ supported: false, reason: 'not-windows' }`.
    2. Build do Windows: `os.release()` devolve `"10.0.<build>"`; parsear o
       terceiro componente com `Number.parseInt`. Se não parsear, NÃO reprovar
       por isso — seguir para o passo 3 e deixar o `start()` decidir (o portão
       de versão é barato e falível; o portão que vale é tentar). Se parsear e
       for `< MIN_WINDOWS_BUILD_FOR_PROCESS_LOOPBACK` ->
       `{ supported: false, reason: 'windows-too-old', detail: release }`.
    3. `loadModule()` dentro de try/catch. Falhou -> `{ supported: false,
       reason: 'addon-unavailable', detail: String(err) }`. Cachear o resultado
       do require (sucesso e falha) — não tentar carregar 100 vezes.

    **`startScreenShareAudioCapture(send): ScreenShareAudioStartResult`.**
    - Se já houver captura ativa, PARAR a anterior antes de criar a nova. Uma
      instância = uma captura; `start()` numa instância já iniciada LANÇA
      (`"Capture already started on this instance"`). Sempre `new LoopbackCapture()`
      por transmissão, nunca reaproveitar.
    - Chamar `isProcessAudioSupported()`; se reprovar, devolver
      `{ ok: false, reason, detail }` — sem tentar nada, sem tocar no addon.
    - `capture.start(process.pid, false, cb)`.
      **O `false` é o coração da fase**, e precisa de comentário do tamanho da
      decisão: `false` = `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`,
      ou seja "capture o sistema inteiro, TIRANDO este processo e seus filhos".
      `process.pid` é o PID do main, e o serviço de áudio do Chromium (que toca
      a voz dos outros participantes) é um processo utilitário filho do
      processo-navegador, dentro dessa árvore. Registrar no comentário que essa
      última afirmação é a PREMISSA MAIS FRÁGIL da fase inteira: é coerente com
      a arquitetura do Chromium mas não há afirmação oficial explícita, e é o
      item nº 1 do checkpoint humano 08.6-06. Se ela for falsa, a voz dos
      outros continua entrando e a fase precisa de outro desenho.
      Registrar TAMBÉM que o preço aceito do modo EXCLUIR é o vazamento: vai
      junto o Spotify, a notificação do Windows, o vídeo da outra aba.
    - Envolver o `start()` em try/catch. O addon lança
      `Error("Failed to start loopback capture (HRESULT 0x...)")` quando a
      ativação falha. Devolver `{ ok: false, reason: 'start-failed', detail: String(err) }`
      e LOGAR o erro inteiro: o HRESULT é o número que distingue "Windows velho
      demais" de "outra coisa".
    - No sucesso: armar o watchdog, emitir `{ kind: 'capturing' }` e devolver
      `{ ok: true, format: { sampleRate: 48000, channels: 2, bitsPerSample: 16 } }`.
      Comentar que o formato é FIXADO no C++ do pacote
      (`LoopbackCapture.cpp:171-175`) e não é negociado: `GetMixFormat()`
      devolve `E_NOTIMPL` no dispositivo virtual de process loopback, e o
      pacote contorna pedindo `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM`. Essa
      armadilha clássica já está resolvida dentro do pacote.

    **O callback de chunk.**
    - Encaminhar por `send(SCREENSHARE_AUDIO_CHANNELS.CHUNK, chunk)`.
      ~100 mensagens/s de ~1,9 KB (192 KB/s) — carga trivial para o IPC.
    - Contar chunks e bytes num contador para o log e para o watchdog.
    - O callback NUNCA pode lançar para dentro do addon (a entrega vem de uma
      `Napi::ThreadSafeFunction`): envolver o corpo inteiro em try/catch e
      logar.
    - Se a janela já foi destruída, ignorar em silêncio e agendar `stop()`.

    **Watchdog de silêncio.**
    `setTimeout(SILENCE_WATCHDOG_MS)` armado no start; o PRIMEIRO chunk o
    cancela. Se disparar, emitir `{ kind: 'no-audio-yet' }` e logar. NÃO parar
    a captura — pode ser só um trecho quieto (o addon descarta buffers
    silenciosos). O objetivo é falhar de forma LEGÍVEL, e não mudo: existe app
    cujo áudio simplesmente não aparece no process loopback (issue #414 do
    `Windows-classic-samples`, com o Teams entregando buffers de zeros).

    **`stopScreenShareAudioCapture(): void` — idempotente, e chamada de TODO
    caminho de saída.**
    - Sem captura ativa: no-op silencioso.
    - Limpar o watchdog, chamar `capture.stop()` dentro de try/catch, zerar o
      estado, emitir `{ kind: 'stopped' }`, logar chunks/bytes totais.
    - Comentar que `stop()` BLOQUEIA a thread que chama até o Media Foundation
      confirmar a parada (comentário explícito no `LoopbackCaptureWrap.cpp`) —
      dezenas de ms de event loop do main travados. É aceito na v1 e é o
      principal argumento para migrar para `utilityProcess` depois; registrar
      como evolução conhecida, não como dívida esquecida.

    **`registerScreenShareAudioHandlers(getMainWindow)`.**
    Mesmo molde de `registerScreenShareHandler`: guarda `registered` contra
    registro duplo com `console.warn`, `getMainWindow` resolvido no momento do
    uso (não no registro — a janela não existe em `app.whenReady()`).
    - `ipcMain.handle(START)` -> `startScreenShareAudioCapture(...)`, sempre
      resolvendo com um `ScreenShareAudioStartResult`, NUNCA rejeitando.
    - `ipcMain.on(STOP)` -> `stopScreenShareAudioCapture()`.
    - `webContents` do renderer recarregando (`did-start-navigation` /
      `destroyed`) -> `stopScreenShareAudioCapture()`. Sem isto, um F5 no
      renderer deixa o WASAPI capturando e 100 callbacks/s indo para uma janela
      que não existe mais — é a Armadilha 5 da pesquisa, que é o Pitfall 2 da
      Fase 8 com outra roupa.
    - `app.on('before-quit')` -> `stopScreenShareAudioCapture()`.

    **`src/main/index.ts`:** importar e chamar
    `registerScreenShareAudioHandlers(() => mainWindow)` dentro de
    `app.whenReady()`, imediatamente ao lado da chamada existente de
    `registerScreenShareHandler(() => mainWindow)`. Nada mais neste arquivo.
